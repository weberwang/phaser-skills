# Phaser 工作流 App 迁移规格

版本：2026-09-05（显示层子任务修订）。依据：当前仓库文档、控制脚本、校验契约及已明确的用户要求；本次增加“所有显示层先记录为子任务，宿主继续推进、子任务按依赖并行准备”。

本文用于迁移流程与业务规则，不表示 App 已实现下述能力，也不授权测试、发布或其他外部操作。

## 1. 阅读约定与不可变原则

- **现有规则**：当前控制面、契约或有效流程要求。文末列出来源。
- **迁移建议**：为 App 增加的实体、界面、调度与可靠性设计，不冒充现有脚本功能。
- 下文 `Nxx` 是建议的 App 节点编号，不是仓库已有枚举；各节点的业务规则沿用现有流程。
- “人工确认”是具体设计/需求选择；“操作批准”是特定高影响操作授权；“测试等级选择”是验证范围授权。三者不可相互替代。
- 项目阶段、Work Item 状态、视觉 V 阶段、执行单元状态、资产状态、阻塞原因必须分别存储，不能合成一个进度字段。
- 未取得真实产物、用户消息或成功运行证据，不得以代理文字声明、默认值或静默等待结束代替。
- 全部授权场景与功能关闭前，不得用首个可玩场景、资源加载成功或一次截图代替项目完成。
- 所有显示层统一记录为宿主子任务，包括 HUD、弹窗、抽屉、Toast。未就绪者先列待办，不自动抢占宿主主线；宿主满足自身前置即可继续，子任务按依赖并行推进，最终 V4 联合验收必须全部闭合。常驻层拆成子任务也保留主图归属与冻结视觉事实。
- 不自动创建分支或 worktree；不自动真机验收；测试与高影响操作遵循各自授权。

### 1.1 本轮必须落实的 V2 规则

1. 先冻结参考目标，再输出拆解图；人工可以修改拆解并确认。
2. 拆解确认前不能进入布局阶段；布局只消费最终确认的拆解元素及冻结参考图。
3. 布局是从拆解推导出的**唯一方案**，不是重新设计，也不是多个方案供选择。
4. 保留确认元素的顺序、原图位置、尺寸和构图；禁止为了“更美观”重排元素或重新生成参考效果图。
5. 左/中/右、上/中/下主要由原图构图、视觉重心与元素语义判断；几何测量服务工程参数和验证，不能替代视觉判断。
6. 布局图是在原图上框出父子容器；同层级同色；空容器也框出；右侧说明父容器与子组件的相对位置。
7. 拆解图与布局图是两张独立 PNG，分别允许人工修改、分别确认。布局确认不能替代拆解确认。
8. 修改上游身份后，受影响的下游方案、确认和证据失效；不得偷偷沿用旧确认。

## 2. 总体流程与四个不同维度

### 2.1 项目业务主线

```text
需求与范围
  → 全局视觉 brief → 恰好三张同条件候选 → 人工选定一张 → 全局基线冻结
  → 场景无关基础工程
  → 按授权范围逐场景生产
      V0 分流
      V1 场景规格、主参考图、本次完整显示层上下文与合同冻结
         └ 未就绪显示层：登记子任务 → 由指定责任方按依赖并行推进
      V2 状态分析 → 原子拆解 → 拆解图 → 人工修改确认
         → 唯一布局推导 → 布局图 → 人工修改确认 → 生产计划冻结
      V3 正式资源生产 → 资源级验收 → 宿主同屏组合预验收
      正式 SCENE / DISPLAY_LAYER 功能实现
      V4 所有弹窗待办闭合后，运行态接入、交互重放、视觉/功能/响应式联合验收
  → 全部授权场景完成 → 跨场景集成与完整验证
  → 精确 A4 批准 → 正式入口集成
  → 如需发布：独立发布 Work Item → 对应批准 → 构建/外部配置/发布 → 留存结果
```

旁路：任何节点都可能等待用户输入、修复、重新验证，或在冻结事实真正失效时返回最早受影响节点。不能一律从头再来。

### 2.2 App 顶层展示阶段

| 展示阶段 | 内容 | 完成边界 |
| --- | --- | --- |
| requirements-scope | 需求、范围、规格、授权 | 最小充分事实与边界确定 |
| global-baseline | 三候选与人工选定、静态基线 | 唯一选择与基线身份有效 |
| foundation-engineering | SHARED / MODULE 基础工程 | 场景无关基础能力验证完成 |
| scene-production | 各场景及显示层 V0–V4 | 全部授权场景的功能与证据闭合 |
| global-integration-validation | 跨场景验证与正式集成 | 全部适用集成门通过 |
| release | 独立发布流程 | 实际获授权操作完成，有真实回执 |

这些是展示投影，不是控制权威；事实冲突或未知时显示未知，不能猜进度。

### 2.3 视觉阶段

| 阶段 | 责任 | 关键完成事实 |
| --- | --- | --- |
| V0 | 判定任务路线及参考图是否为正式视觉目标 | 唯一路线、适用性与理由 |
| V1 | 定义并冻结视觉目标与工程合同 | 参考身份、状态、视口、预算、响应式、显示层合同 |
| V2 | 先拆解确认，再布局确认，形成生产方案 | v2-production-planning-complete |
| V3 | 生产并验收正式资源、宿主同屏预验收 | v3-formal-acceptance-complete |
| V4 | 正式代码接入与运行态联合验收 | v4-runtime-integration-candidate；不等于发布完成 |

### 2.4 Work Item 控制状态

以下迁移来自当前控制脚本；实际还受动作级别、阶段和证据守卫限制，并非列出就可任意跳转。

| 当前状态 | 允许的下一状态 |
| --- | --- |
| INTAKE | BASELINE、BLOCKED |
| BASELINE | PROPOSAL、BLOCKED |
| PROPOSAL | REVIEW、RETURN、BLOCKED |
| REVIEW | VALIDATING、IMPLEMENTING、RETURN、BLOCKED |
| IMPLEMENTING | VALIDATING、RETURN、BLOCKED |
| VALIDATING | PASSED、RETURN、BLOCKED |
| PASSED | INTEGRATING、COMPLETE、RETURN、BLOCKED |
| INTEGRATING | COMPLETE、RELEASE_APPROVAL_REQUIRED、RETURN、BLOCKED |
| RELEASE_APPROVAL_REQUIRED | RELEASING、RETURN、BLOCKED |
| RELEASING | COMPLETE、BLOCKED |
| COMPLETE | 无 |
| RETURN | BASELINE、PROPOSAL、REVIEW、IMPLEMENTING、BLOCKED |
| BLOCKED | BASELINE、PROPOSAL、REVIEW、IMPLEMENTING |

`USER_INPUT_REQUIRED` 是阻塞类型，不是 `globalState`。A1 可以 REVIEW→VALIDATING，不必虚构代码实施；发布状态要求独立 release Work Item。恢复不能绕过当前守卫直接跳回任意旧状态。

### 2.5 每个工作项都要执行的控制步骤

业务节点与控制步骤交织运行，不能把“审计/验证”误解成项目最后才做一次。

| 控制步骤 | 必做事项 | 退出事实 |
| --- | --- | --- |
| 基线捕获 | 读取范围、原有代码/规格/资源，记录不可变 baseline 身份与现有改动 | 可判断本工作项实际差异 |
| 候选与计划 | 定义目标、模块 API/状态边界、文件所有权、预期新增/删除、命令和退出条件 | implementation package 与当前候选/差异绑定 |
| 评审与冻结 | 执行适用 F0/F1、领域检查；实质取舍取得用户决定 | 当前计划可实施，不存在未解的决定性问题 |
| 派发与执行 | 先检查委派/并行前置，再按冻结顺序派发；只在 IMPLEMENTING 初始化执行状态 | 当前单元真实产物与结果可核对 |
| 差异审计 | 对真实代码/资源变化与计划、所有权做比对 | 当前 diff audit，有偏差则先处理 |
| 选择与运行验证 | 推荐等级/命令，获得用户选择，运行适用检查 | 当前 batch 的实际证据与未覆盖项明确 |
| 门检查与交接 | 校验身份、新鲜度、适用 F 门和退出条件；必要操作另取 F4 | PASSED、合法交接/集成或 COMPLETE |

只有控制面可以改变 globalState 或写操作审批账本；领域执行者提交产物与事实，不自行宣布门通过。以上每一步失败都进入第 8 节的处理，而不是直接跳到下一业务节点。

## 3. 节点详细规格

每个节点均列输入、执行责任、产物、人工点、放行和失败处理。具体页面可合并展示，业务门不得合并或省略。

### N01 接收任务与识别范围

- 输入：用户原始需求、仓库/项目身份、现有 Work Item、当前候选及已有产物。
- 执行：控制面识别新建、继续、变更、诊断或仅咨询；判断是否属于 Phaser 生命周期；读取现状，保护未提交改动。
- 产物：任务范围、目标、验收边界、已知/缺失事实、拟用能力与动作级别。
- 人工点：仅对实质缺失或歧义请求输入；不把提问当成已获授权。
- 放行：对象、目标与允许动作明确。失败：范围不明进入用户输入阻塞；普通 Git/文件/浏览器任务不强塞进此生命周期。

### N02 初始化控制记录与授权

- 输入：N01 范围、项目控制目录现状、用户授权原文。
- 执行：控制面创建或加载 Work Item、授权与审批记录；新项目仅在授权后执行一次控制脚手架初始化，重复初始化拒绝。
- 产物：workItemId、初始状态、动作级别、taskAuthorization、审批/决策关联；初始化不代写 GDD/TDD 等业务规格。
- 人工点：A0–A3 按任务授权覆盖；A4–A6 必须针对精确操作另行批准，不能从“完成任务”推断。
- 放行：F0 授权有效、作用域匹配。失败：补授权/字段；不得把待批准操作先执行再补账。

### N03 收敛需求与项目规格

- 输入：产品目标、玩法、平台、用户、范围、资源和商业约束。
- 执行：制作/玩法/架构责任方收敛最小充分事实，定义核心循环、所有授权场景、输入状态、进度/失败/奖励、数据与非功能要求；按适用范围定义预算。
- 产物：project-profile.yaml、GDD.md、TDD.md、qa-plan.md、platform-matrix.md 等；缺失事实带责任人与阻塞影响。
- 人工点：产品、设计、架构、预算、合规和数据等实质取舍由用户决定；必要时做限定范围原型，不默认扩大生产实现。
- 放行：F1 规格可执行、验收可观察、无决定性歧义。失败：局部补规格；真实方向变化建立变更记录。

### N04 建立全局视觉 brief

- 输入：批准的项目规格、世界观、目标受众、视觉/性能限制。
- 执行：视觉责任方明确形状、比例、镜头、色彩、材质、光照、描边、密度、字体、图标、面板、动画/VFX、主锚点与分系统锚点，以及允许变量和禁止项。
- 产物：候选生成 brief、同条件约束与参考清单；此时不是已冻结基线。
- 人工点：未明确且影响方向的选择先获得决策。
- 放行：可在同条件下比较候选。失败：补齐 brief，不直接开始批量资产或场景效果图生产。

### N05 生成全局三候选并人工选择

- 输入：N04 brief 和统一生成条件。
- 执行：生成恰好三张全局候选效果图，保留提示词、输入、模型/版本及真实输出身份；同屏展示三张。
- 产物：三张候选、生成记录、唯一 SINGLE_HUMAN / CONFIRMED 选择及真实用户消息。
- 人工点：用户明确选择确认一张；无回复、代理偏好或机器评分不能代选。
- 放行：候选数量与唯一人工选择有效。失败：缺候选补齐；用户要求修改时形成新版本并重新选择，保留旧记录。

### N06 冻结全局静态基线

- 输入：N05 唯一选定候选及其证据。
- 执行：冻结 visual-baseline.md 的基线正文与身份、风格指纹、全部锚点；探索和后续证据写入 visual-design.md 等，不能悄悄改冻结正文。
- 产物：globalVisualBaselineSelectionRef（文件及 SHA）、global-static-baseline-frozen、基线版本。
- 人工点：选择生产者的 workItemId 保留原值；后续消费者不得为方便而重写成自身 ID。
- 放行：选择和基线文件身份可复核。失败：修复绑定；真正变更全局方向需新决策、失效分析与新基线。

### N07 冻结基础工程实施包

- 输入：全局基线、架构规格、当前代码基线。
- 执行：只规划 SHARED / MODULE 的最小骨架、配置、状态、输入、平台、资源基础设施与测试支撑；建立文件与状态所有权、顺序、命令和退出条件。
- 产物：foundation-only implementation package、executionUnits、fileOwnership、候选/差异身份。
- 人工点：如架构边界有实质取舍先确认；不得提前申请无对应候选的集成批准。
- 放行：基线选择与冻结状态完整；无具体场景玩法、UI/布局、正式可见资源消费、正式 Scene 接入。失败：越界部分移入场景工作。

### N08 实施并验证基础工程

- 输入：N07 冻结实施包和 A3 授权。
- 执行：进入 IMPLEMENTING 后初始化执行状态，按单元顺序实施；只在授权测试等级内验证，记录实际文件差异与命令证据。
- 产物：基础工程候选、单元结果、diff audit、适用 F0–F3 证据及交接。
- 人工点：先推荐测试等级/理由/命令，再等待明确选择；不得自动启动真机。
- 放行：所有当前单元通过，工程范围合规。失败：当前单元修复重验；基础接口改变触发受影响规格和计划重审。

### N09 场景登记与 V0 分流

- 输入：授权场景集合、具体场景/资源请求、既有视觉合同。
- 执行：确定原子资源、组件/资源集、场景/视觉系统/重做路线；判断指定图是否为正式运行画面的冻结目标。
- 产物：唯一路线、effect-image 适用性和理由、场景身份与依赖。
- 人工点：用途不清时确认图片是正式目标还是灵感。
- 放行：正式目标即使零新资产、全复用/程序实现也必须走参考还原合同；只生成新资源不自动触发 effect-image。原子资源跳过 V1 必须有全部有效前置合同，否则升级路线。
- 失败：范围变化重做 V0；不能用资源数量决定是否绕过参考还原。

### N10 定义场景功能与必要灰盒

- 输入：GDD/TDD、全局基线、场景范围。
- 执行：玩法方定义状态、交互、进入退出、胜负/暂停等；视觉方定义每状态第一视觉目标、信息优先级、可供性、反馈时序和遮挡限制；仅对尚未证明的结构/交互/节奏做必要灰盒。
- 产物：场景功能规格、玩法视觉契约、必要运行/灰盒证据、纹理/帧数/内存/过绘/Draw Call 等项目预算。
- 人工点：实质取舍记 USER_DECISION；已有明确冻结事实且不改变它们可记 AUTO 与依据。灰盒不强制成为最终换皮模板。
- 放行：语义、状态所有权、预算和可观察验收明确。失败：留 V1 或返回真正受影响的 GDD/合同。

### N11 冻结 V1 主参考与响应式合同

- 输入：N10 规格、全局基线、生成或用户提供的参考图。
- 执行：生成/接收 scene master/reference target；登记来源权属、版本、SHA、视口、DPR、目标状态、对比条件、整屏构图、初步拆解及技术冲突；冻结项目忠实度容差和批准例外。
- 产物：主参考图、scene_reconstruction_contract、初步还原草案、布局/响应式合同。
- 人工点：影响冻结视觉事实的技术取舍需精确确认；provided 记录真实外部来源，不能伪造 ImageGen 过程。
- 放行：viewport、Canvas、逻辑坐标、safe area 的关系，缩放/锚点/断点策略，背景覆盖，裁切/留白/拉伸许可，动态文本/显隐/滚动/触控/resize/横屏策略齐全。缺响应式合同阻断 V2。
- 失败：修复绑定；冲突确需改变目标时先变更冻结参考，不让下游自行改图。

### N12 登记显示层：完整规划或待办分流

- 输入：宿主场景主参考与状态、HUD/弹窗等功能需求。
- 执行：盘点全部层并作为宿主子任务；本次完整规划放入 inventory，登记状态、触发/关闭、输入阻断、z-order、遮罩、焦点恢复、响应式及互斥/共存。未就绪者显式放入 deferred_layers，记录负责人和原因，不自动切换主线去生成；所有合法显示层类型均可分工。
- 产物：完整 inventory、deferred_layers 待办、persistent_layer_ids；仅完整层要求每个 required 瞬态状态的宿主上下文参考图与绑定。
- 人工点：用户或指定执行者可另行并行处理弹窗；未确定的弹窗产品语义留在该待办，不扩大为宿主全面阻塞。
- 放行：合法待办不因缺独立上下文图阻断宿主显示层规划门；宿主其他前置仍须满足。HUD 必须 persistent，常驻待办仍在主图与 persistent_layer_ids 中，瞬态层不得混入默认主图。完整瞬态层图必须是 host-scene-context、isolated_only=false、匹配宿主视口/SHA；待办不伪造图和 target SHA。

### N32 精确批准并执行 A4 正式集成

- 输入：PASSED 候选、具体正式入口/迁移/删除等操作及影响面。
- 执行：控制面准备精确操作批准请求，展示候选、目标、差异、风险、回退与证据；批准后仅执行批准范围。
- 产物：Approval Ledger、INTEGRATING 执行结果、正式集成证据。
- 人工点：真实用户明确批准；任务授权、设计确认、测试通过均不能替代 F4。
- 放行：批准对象未漂移、F4 有效、实际操作完成。失败：候选变更使批准失效；操作失败记录结果并按授权边界处理，不自动扩展删除或迁移。

### N33 完成开发工作项与交付

- 输入：适用开发/集成证据与所有退出条件。
- 执行：记录完成范围、产物、验证等级及结果、未执行项、剩余风险与交接；只关闭真正完成的 Work Item。
- 产物：COMPLETE、交付摘要、可追溯产物引用。
- 人工点：开发完成不等于发布获准；提交/推送等普通仓库操作仍按用户请求处理。
- 放行：无必需未完成工作。失败：保留真实阻塞状态，不为了结束对话强行 COMPLETE。

### N34 建立独立发布工作项

- 输入：已通过的可发布候选、目标渠道/平台、实际发布意图。
- 执行：独立 release Work Item 登记版本、构建配置、渠道、隐私/年龄/广告/IAP 等适用要求、回退和监控；新增渠道独立平台矩阵条目。
- 产物：release-checklist、platform-matrix、发布候选身份、拟执行 A5/A6 操作列表。
- 人工点：按实际操作请求授权；不把开发 Work Item 的批准继承为发布批准。
- 放行：发布范围与目标明确、必要材料齐全。失败：等待缺失决策/素材/权限；仅准备就绪不得声称已上线。

### N35 执行获批构建与外部配置

- 输入：N34 候选、具体 A5 等授权、环境与凭据引用。
- 执行：按实际任务构建并记录可复现命令、版本和包哈希；仅获授权时上传构建或修改后端/渠道配置；密钥由受控存储提供，不写入文档或日志。
- 产物：构建包及 SHA、上传/配置回执、环境与操作结果。
- 人工点：外部写入、费用和目标变化分别受授权约束；测试等级不授权这些动作。
- 放行：成功回执对应批准候选。失败：明确部分成功/失败及外部状态，不盲目重复非幂等操作。

### N36 执行获批真机/提交/发布/线上回滚并关闭

- 输入：精确 A6 批准、目标设备或渠道、当前候选与操作方案。
- 执行：只执行获授权的真机验收、商店提交、正式发布或线上回滚；记录各渠道实际结果和需要的后续工作。
- 产物：设备/渠道/版本/时间/操作回执、发布或回滚证据、最终交付状态。
- 人工点：不自动真机、不自动提交/上线、不因失败自动线上回滚；所需新操作重新取得授权。
- 放行：实际目标操作成功且适用退出条件满足才 COMPLETE。失败：保留真实状态与责任人；等待审核不等于上线成功。

## 5. 场景、弹窗与并行调度

### 5.1 实现边界

- 场景为 `SCENE`；HUD/modal/popup/drawer/toast 等显示层为 `DISPLAY_LAYER`，绑定宿主，不创建第二套全局状态机。
- 全部显示层都可作为待办子任务分工；持久层始终保留宿主主图归属。本次完整规划的瞬态弹窗逐 required 状态冻结宿主同屏上下文图；未就绪者先列待办，不自动补图。单独弹窗图可辅助但不能代替后续同屏图。
- 单个弹窗也需要适用的 V0–V4 事实和验收，但复用宿主/场景的全局基线与统一场景 V2 根计划，不重复做全局三候选。
- 多个弹窗各有 layer_id、状态、资源、上下文引用和验收记录；共用的宿主入口/路由/状态接口由明确所有者集成。
- 待办弹窗可由其他执行者并行推进自身参考、拆解确认、布局确认、资源生产；正式代码仍必须满足自身前置，不能把“宿主可以继续”解释为弹窗可跳过 V2/V3。
- 宿主可先完成公开触发事件/接口，不因弹窗延期删除主图按钮或重新布局，也不加载未验收弹窗资源；最后由明确所有者补齐接线并验收真实行为。
- “弹窗可独立实现/收集证据”与“必须宿主同屏联合验收”同时成立，不应说成只能整体做、或完全独立验收就能完成场景。

### 5.2 当前执行计划实际约束

| 单元类型 | 可并行性 | 身份与限制 |
| --- | --- | --- |
| SHARED | SERIAL | 最先；串行理由明确 |
| MODULE | SERIAL 或 PARALLEL | 场景无关模块；按冻结组调度 |
| SCENE | SERIAL 或 PARALLEL | sceneId 非空；当前 V2/V3 前置有效 |
| DISPLAY_LAYER | SERIAL 或 PARALLEL | displayLayerId/hostSceneId 非空、sceneId=null；可连续有多个同宿主显示层 |
| INTEGRATION | SERIAL | 最后；负责共享集成边界 |

- `executionUnits` 数组就是冻结顺序，不可按名称或 ID 重新排序。
- 并行组至少两个、相邻、同阶段；每个单元文件路径和状态命名空间独占，包含层级重叠检查。
- SERIAL 必须有 serializationReason 且 parallelGroup=null；PARALLEL 必须有组且串行理由为空。
- 同组成员不是彼此的前置；全组当前结果 PASS 后才释放下一阶段。单元结果通过 unit-check 推进。
- 不能因为有多个弹窗就自动并行；必须通过依赖、路径和状态检查。

### 5.3 App 建议增加的依赖守卫

当前脚本允许 SCENE/DISPLAY_LAYER 同一阶段分组；并行前应确认宿主公开接口已冻结，而非强制宿主代码全部完成。待办先并行准备，进入代码并行组前双方前置必须有效；嵌套弹窗的真实依赖应单独记录：

```text
宿主主线：参考/拆解/布局确认 → V3 → 场景代码实现 ───────┐
弹窗支线：登记待办 → 参考/拆解/布局确认 → V3 → 弹窗实现 ─┤
                                                     ↓
                         全部待办关闭 → 单一所有者接线 → V4 联合验收
```

两条业务支线可并行推进，不代表两个不受控的全局状态机。代码并行遵守当前工作项证据、冻结计划和互斥所有权；父弹窗是子弹窗真实功能依赖时串行。共享接线可归宿主单元或合法 INTEGRATION 单元，不新增未经契约支持的单元类型。

### 5.4 全部显示层子任务记录与完成边界

HUD、modal、popup、drawer、toast 统一记为宿主场景下的子任务，可分派不同负责人按依赖并行推进；不是要求宿主主线先完成它们。当前机读待办载体是按需数组 `display_layer_planning.deferred_layers`，`layer_id` 为稳定子任务键、`host_scene_id` 为父场景关联，每项严格为以下结构；没有延期可省略，但不能漏记已知未完成子任务。

```json
{
  "layer_id": "settings-popup",
  "host_scene_id": "play",
  "type": "popup",
  "persistence": "transient",
  "in_scene_master": false,
  "owner": "弹窗实现负责人",
  "reason": "参考上下文图待独立制作，宿主继续实现"
}
```

ID、宿主、负责人、原因必须非空；类型支持 hud/modal/popup/drawer/toast；不得与 inventory/其他待办重复。HUD 必须 persistent；常驻层的 in_scene_master=true 且必须在 persistent_layer_ids 中，瞬态层为 false 且不得在该列表中。完整层关系可引用待办 ID。字段由共享显示层合同与对应 JSON schema 校验，待办不是图证据，也不是 PASS。

App 建议为每个子任务单独展示当前 V 阶段、执行状态、阻塞原因、产物与确认记录；这些是子任务进度，不覆盖父场景 globalState，也不把所有子任务强行串行。子任务转为完整 inventory 后仍保留其历史与父子关联；不能从待办列表消失就自动认定实现完成。这些进度字段属于 App 实体设计，不往上述严格待办 JSON 塞入未定义字段。

建议子任务界面区分“待规划、规划中、实现中、待联合验收、完成”：其中“待联合验收”表示子任务自身产物已就绪但宿主接线/同屏证据尚未闭合，不是通过。该展示状态仅为 App 建议，不新增当前 globalState/V 阶段机器枚举。

V1–V3 接受合法待办；V4 拒绝非空待办。完成弹窗前置后将同 ID 转入完整 inventory，补齐正式消费及交互重放，更新受影响版本/证据，再联合验收。取消需求必须是显式范围变更，不能仅从数组删掉。数据库层的历史追踪和防止“删除即完成”仍需 App 按审计/变更规则实现，当前校验器不能凭一份最新 JSON 推断被抹掉的历史。

下表是迁移时应保存的业务实体。现有 JSON 工件可作为初期载体；数据库表名、内部 ID 和补充字段是 App 实现选择，不代表当前 schema 已有。

| 实体 | 必须保留的信息/关系 |
| --- | --- |
| 项目 | 仓库身份、授权场景集合、平台范围、当前全局基线引用 |
| Work Item | ID、类型/范围、globalState、动作级别、基线/候选/diff/batch、授权、交接与变更关系 |
| 任务授权 | 用户原文、作用域、允许动作、有效绑定；不代替 A4–A6 批准 |

| 参考目标 | 原文件、来源权属、SHA、版本、scene/state、viewport/DPR、宿主/层绑定 |
| 拆解方案 | 状态分析、component/state/placements、按序元素、region、生产合同、技术 JSON、图与 SHA |

| 人工决策/确认 | 具体类型、展示版本、用户原文/消息身份、结论、对象及全套 SHA、时间、失效关系 |
| 用户解析账本 | 控制面根据真实用户消息生成的 user-resolution/receipt/entry 关联及身份；实现者不可自行写入 |
| 资源与生产单元 | ID/纹理键、场景或共享归属、component×state、路径、方法/输出/生成记录/授权、状态、SHA |
| 实施包 | 冻结执行顺序、文件/状态所有权、验收命令、V2/V3 前置、visualProductionUnits、计划指纹 |
| 执行单元与结果 | unitId/type/owner、串并行组、路径/状态、实际输出、PASS/FAIL 和当前候选身份 |
| 差异审计 | 实际新增/改动/删除、预期所有权核对、baseline/candidate/diff、时间 |
| 验证批次/证据 | 命令、真实日志/文件/SHA、环境与数据源、实际结果、适用门、退出条件、未覆盖项 |
| 操作批准 | 精确动作与目标、候选/证据绑定、批准用户消息、状态、失效原因 |
| 变更与回退 | 根因、范围、最早受影响阶段、失效产物、旧 batch、新基线、记录/解决时间 |

资产状态包括 planned、producing、review、accepted、rejected、replaced；被拒绝/替换仍保留原归属和审计历史。共享资产通常要求至少两个 confirmed 场景，运行必需资源可显式使用 runtime-required 例外。

### 6.1 确认防错绑与身份规则

- 用户看到的图/JSON/决策版本与提交确认必须完全相同。App 不得在用户查看期间自动替换为另一版再接收旧确认。
- 当前控制流程使用 `.phaser-workflow/user-resolutions/` 下受控账本、条目/回执哈希、baseline blob 与 prerequisite 引用建立可信链；执行者不能伪造或拥有这些路径。
- 实施包场景/状态确认采用当前复数 `visualDecompositionConfirmations[]` 规则；不要把根计划等其他上下文的单数结构机械替换。
- canonical 哈希可排序对象键；**不能排序具有语义顺序的数组**，尤其 decomposition_elements、executionUnits。moduleIds 等明确集合型字段才按契约排序去重。
- App 若换成数据库/对象存储，应提供等价不可变版本与审计链；不能说“有数据库记录”就等价于现有文件/SHA/基线校验。

### 6.2 生产合同枚举与边界

| 字段 | 当前允许值/规则 |
| --- | --- |
| 实现分类 | generate-now、reuse-existing、runtime-program |
| production_method | imagegen、authored-raster、authored-svg、phaser-graphics、runtime-program、reuse |
| delivery_kind | raster-image、vector-image、runtime-drawing、runtime-program、existing-asset |
| image_generation_required=true | 必须 imagegen + raster-image，交付独立位图及完整记录，不能用其他枚举替代 |
| ImageGen 文件 | 源/运行输出 PNG 或 JPEG；透明输出仅 PNG；一般 authored-raster 的格式范围不能套用于 ImageGen |
| atlas_allowed | ImageGen 固定 false；其他方法按显式合同与完整切片映射判断 |

枚举存在不代表任意区域都能选用它；实际方法必须符合该区域冻结的 owner、生产合同和 substitution_policy。界面不能为了方便提供“自动降级为程序绘图”绕过审计。

## 7. 授权、质量门与测试

### 7.1 动作级别与门

| 级别 | 含义 | 授权边界 |
| --- | --- | --- |
| A0 | 检查/分析 | 不实施生产改动 |
| A1 | 规格/候选方案 | 不默认授权正式生产实现 |
| A2 | 隔离原型 | 限原型范围 |
| A3 | 正式生产代码、QA 构建等 | taskAuthorization 可覆盖；测试仍按用户选择 |
| A4 | 正式集成、迁移、正式入口、删除旧实现等 | 精确操作批准 |
| A5 | 外部构建上传、后端/渠道配置等 | 精确操作批准，声明外部动作 |
| A6 | 真机、商店提交、发布、线上回滚等 | 精确操作批准，绝不自动执行 |

F0=授权/流程，F1=规格，F2=领域质量，F3=工程运行证据，F4=具体高影响操作。

这些风险门不是五次顺序人工审批；视觉 F2 使用确定性 MACHINE 证据，不能自动推导为所有领域免独立审查。通用证据契约中 A3–A6 的 F2 独立性要求仍需遵守，A1/A2 可允许 SELF。

G0=项目准备，G1=全部授权功能实施，G2=完整候选验证/集成，G3=发布；不能把 G2 用来补漏 G1。

### 7.2 测试等级与 App 行为

| 等级 | 范围 |
| --- | --- |
| T0 | 不运行测试，仅检查本次改动 |
| T1 | 最小相关测试、类型检查或 lint |
| T2 | 受影响模块单元/集成、类型、lint、必要构建 |
| T3 | 全量测试/构建与关键流程冒烟；不含隐式真机/外部写入/发布 |

先展示推荐等级、理由、覆盖和拟执行命令，再等待人工选择。未选择显示“待人工选择测试等级”，不执行测试；不得从历史其他工作项的 T2 推断新任务授权。结束记录实际等级、结果、失败、未执行项。

响应式验证按合同覆盖基准/最窄/最宽、断点邻近、同宽矮高、方向切换、默认/大字体、长文案、零/非零安全区；记录实际 viewportRect/canvasRect、resize 前后稳定帧与坐标关系。FIT 配置或一张截图不是响应式通过证据。阈值必须来自项目合同，不能自造通用百分比。

## 8. 失败、回退与恢复

| 情况 | 处置 | 不应做的事 |
| --- | --- | --- |
| 文件/字段/绑定/输出与冻结方案不符 | repair，保留仍有效的冻结事实 | 为字段错重新请用户选择视觉方向 |
| 同一目标/候选/差异/基线的证据缺失、旧或失败 | revalidate 当前门 | 复用过期日志、直接 PASS |
| 冻结范围/参考/拆解/布局/生产规格真实失效 | 显式 return 到最早受影响阶段 | 任意重启全部项目或偷偷改上游 |
| 用户取舍缺失 | USER_INPUT_REQUIRED 阻塞并列缺失问题 | 把沉默、代理推断记成用户批准 |
| 显示层子任务未就绪 | 显式登记 deferred_layers；宿主满足自身前置可继续，子任务并行推进 | 自动抢占主线、误报子任务已完成或抹掉主图可见事实；最终 V4 不得带待办通过 |
| 外部依赖/权限/操作失败 | BLOCKED 或当前执行失败，留真实状态 | 假造完成或自动扩大外部操作 |

return 必须记录最小 `stage:` / `scene:` / `artifact:` 范围、invalidatedArtifacts、previousValidationBatchId、recordedAt/resolvedAt；清理受影响待批准项、视觉快照、差异审计，按影响使实施包/执行状态失效并更换验证批次，保留历史审计。

典型失效传播：

- 全局基线变更 → 受影响场景参考、V2、资源一致性和后续证据重新评估。
- 拆解元素或其身份变更 → 旧拆解确认及依赖它的布局/生产计划不能继续使用。
- 仅布局关系变更且拆解不变 → 重生成布局图并重新布局确认；不无故重做拆解。
- 正常生产候选推进且冻结设计未变 → 刷新当前工程证据，不自动重复设计确认。
- 代码/差异变化 → 旧候选工程证据和精确操作批准按绑定失效，不能只修改状态字段绕过。

## 9. App 实现建议：页面、调度与可靠性

本节为迁移建议，现有脚本未自动提供完整数据库事务、队列和服务端界面。

### 9.1 最小页面

1. 项目总览：六阶段、全部场景覆盖、真实完成/阻塞/未知，不能只按节点数量算完成。
2. 工作项详情：范围/授权、控制状态、视觉阶段、当前节点、依赖、负责人、下一动作。
3. 全局候选选择：固定三图同屏，唯一选择，展示版本与确认回执。
4. 场景/显示层工作台：宿主主图、完整 inventory 与待办分区、负责人/原因、状态上下文图、关系与证据；待办可派发但不自动抢占宿主主线。
5. 拆解编辑确认：原图 PNG、按序元素、状态/组件/生产分类；修改后重生成再确认。
6. 布局编辑确认：原图父子框、层级树、双轴居中选项、右侧关系说明；禁止隐式重排。
7. 生产与资源验收：component×state 清单、生成/去背/归一化、来源权属、审计和消费证据。
8. 实施调度：冻结顺序、依赖/并行组、文件/状态所有权、屏障、每单元结果。
9. 验证中心：等级选择、命令计划、当前候选/批次、日志、失败/未执行及证据新鲜度。
10. 决策与操作批准中心：两类记录分区，精确对象/版本、风险、用户原文和失效原因。
11. 变更/恢复中心：影响图、repair/revalidate/return、历史版本和最小重跑范围。
12. 发布中心：独立发布工作项、渠道/版本、授权、外部回执，区分准备/上传/提交/上线。

### 9.2 服务端处理顺序

```text
接收动作 → 校验用户身份/权限 → 校验当前状态与产物版本
  → 校验依赖/授权/守卫 → 占用节点或文件所有权
  → 执行获授权动作 → 存储实际产物与证据
  → 确定性校验 → 原子提交结果/事件 → 释放后继节点
```

- 人工确认建议用展示版本+产物哈希作乐观锁；旧页面提交返回“版本已变化”，不自动接受最新版本。
- 对任务启动、确认、生成回调、单元完成建立幂等键；重复消息不重复生成、扣费或推进。
- 执行租约/心跳与结果提交分离；代理中断不等于业务失败，也不等于已完成。
- 外部调用超时先查回执/状态，再决定重试；未知结果不能盲目重放发布等非幂等动作。
- 产物不可变版本化；失败记录不覆盖成功历史；回退建立失效关系而非删除审计历史。
- 调度器只能释放已满足依赖和授权的任务，不能替用户确认图、选择测试等级或批准发布。
- 若封装现有 CLI，保留 status/stage/changed/blocking/next/metadata、workflowView、planFingerprint；`check` 只读，`run` 只推进一次安全控制动作，不会自动替你运行测试、业务实施、服务或外部动作。
- 建议事件包括：任务创建/授权、基线冻结、方案更新、确认接受/失效、执行启动/完成/失败、证据提交、守卫通过/拒绝、回退、操作批准/执行、工作项完成。事件名自定，不冒充现有枚举。

## 10. 源规则冲突与迁移取舍

| 冲突/易误读点 | 迁移采用的规则 | 说明 |
| --- | --- | --- |
| 旧 production/architecture/QA 文案出现 V5、V1→V5 | 只用当前 V0–V4 | 当前视觉阶段契约不支持 V5；旧称运行验收归入 V4 |
| 旧文案“拆解布局同步”“先冻结布局节点” | 拆解确认后才推导布局，布局另确认 | 遵循最新用户要求及已更新布局契约 |
| 旧文案“V2 唯一人工确认” | V2 两个串行确认：拆解、布局 | 全局三候选选择仍是更早独立硬门 |
| “优化布局/多个候选”式理解 | 保序保图，推导唯一布局 | 不重新生成参考、不重新排列确认元素 |
| 文案“模块才可并行” | SHARED/INTEGRATION 串行；MODULE/SCENE/DISPLAY_LAYER 依计划可并行 | 按当前 parallel-plan 实际支持范围；不能忽略依赖 |
| 口头“弹窗全部独立”或“不能独立验收” | 独立实现与证据可行，但必须宿主组合验收 | 不重复全局基线；不得用孤立图替代上下文 |
| V3 与 V4 的重放要求混淆 | V3 同屏组合预验收；V4 四步运行重放 | 按显示层校验合同 |
| 显示层缺图都阻断宿主、自动转去补图 | 所有显示层统一为子任务，未就绪先显式登记待办；宿主满足自身前置继续，子任务可并行准备 | 本轮新要求；保留常驻层主图归属，待办最终阻断 V4；不是完全独立工作项身份或免前置 |
| “整个场景同一 Work Item”与“V2 完成、V3 后续 Work Item”并存 | 场景生命周期作为聚合根；执行工作项可分阶段交接，V2→V3 保留显式 handoff | 这是化解冲突的 App 建议；不要声称当前所有脚本已统一。上线前需统一产品选定策略与相应契约 |
| 单数/复数拆解确认字段的旧说明 | 按各具体 schema；实施包采用 visualDecompositionConfirmations[] | 不做历史兼容双读，也不机械改其他上下文 |
| 旧 v3-ready 或完成话术 | 使用当前实际清单/阶段字段：effect-image/v2-ready、v4-complete 等 | 视觉清单状态与 Work Item COMPLETE 不混淆 |
| 资源“生成完/loaded/used”即完成 | 资源合同、组合、fidelity、运行重放、消费和当前证据均需闭合 | missing=0 只是工程子门 |

优先级：本轮明确用户要求 → 当前有效控制/校验契约 → 与其一致的流程文档。遇到控制契约内部真冲突，标出并统一策略后落地，不能仅靠前端隐藏。

## 11. 迁移验收清单

- [ ] 六个项目展示阶段与 Work Item/V 阶段/执行单元/资产状态分别建模。
- [ ] 授权范围、全部场景与显示层无遗漏；无显示层有显式空清单。
- [ ] 所有显示层可记录子任务及负责人/原因；不抢占宿主主线；HUD 待办仍 persistent 且保留主图归属。
- [ ] 待办不进入缺前置的可执行单元；弹窗就绪后受控更新计划，最终 V4 待办非空拒绝通过。
- [ ] 全局恰好三候选同屏，真实人工唯一选择后才能冻结。
- [ ] 基础工程不提前消费正式场景资源或接入正式 Scene。
- [ ] V0 正式参考图适用性不依赖新增资产数量。
- [ ] V1 参考、宿主上下文、状态、响应式、预算、容差与权属完整。
- [ ] 状态分析先于 component inventory；重复实例与唯一资产区分。
- [ ] 拆解图、技术 JSON 和真实用户确认绑定同一版本。
- [ ] 未确认拆解时布局入口不可执行；禁止旧 layout_nodes 绕过。
- [ ] 布局保持原元素顺序、位置尺寸和构图，双轴支持 center。
- [ ] 布局 PNG 有父子框、同层同色、空容器和右侧关系说明。
- [ ] 布局有独立修改/确认；不产生新参考或多方案选择。
- [ ] 全画布 coverage 完整，production units 与区域/部件/状态一一对应。
- [ ] ImageGen 独立位图、尺寸、透明一次去背、归一化、记录和 SHA 可验证。
- [ ] 复用资源绑定不可变来源；accepted 文件不静默覆盖。
- [ ] V3 有资源级合同审计和宿主同屏预验收。
- [ ] 正式 SCENE/DISPLAY_LAYER 实施受当前 V2/V3 前置约束。
- [ ] 并行组有独占路径/状态、依赖、当前结果与全组屏障。
- [ ] V4 有宿主四步重放、真实消费、fidelity、响应式、功能/性能联合证据。
- [ ] 全部授权 G1 完成后才进行 G2 完整候选验证。
- [ ] 测试先选等级；未执行不显示通过；不自动真机。
- [ ] 设计确认、测试选择、A4–A6 操作批准完全分离。
- [ ] stale 证据、旧页面确认、重复回调和候选漂移不能错误放行。
- [ ] repair/revalidate/return 有明确区分、最小影响范围和审计历史。
- [ ] 发布独立工作项，准备/上传/提交/上线状态真实区分。
- [ ] 图片优化等显式调用分支不被插为默认节点。
- [ ] 第 10 节冲突已在 App 契约、调度和界面中统一，不保留双套旧流程。
