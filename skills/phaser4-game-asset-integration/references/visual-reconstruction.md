# 参考截图或代码驱动的视觉与功能还原

当任务要求根据截图、现有界面、录屏、运行中的 Phaser 场景或源代码进行还原时，完整读取本文件。目标是同时还原可观察功能和视觉表现：先建立可追溯的参考功能契约与视觉基线，再实现、生成、装配并逐状态验收；不得只做截图翻新、裁图替换或静态画面近似。

## 输入归档

1. 记录输入类型、位置、版本、目标场景、视口、设备像素比、游戏状态、操作路径和权属。外部截图或第三方项目只提炼获准借鉴的视觉特征与可观察交互规律，不复制受限角色、商标、独特素材或受保护实现。
2. 保留未经修改的截图、录屏、操作步骤、状态样本和预期结果。截图只能证明单一时刻的可见状态；无法证明的输入响应、状态迁移、计时、随机、失败处理、存档或平台行为一律标为“证据缺口”，不得自行补成参考功能。
3. 代码输入先定位场景、组件、布局、样式、资源加载、输入、规则、状态、动画、持久化和平台入口，再在可复现环境中运行，捕获固定视口截图并记录操作轨迹。仅凭源码猜测最终画面或仅凭截图猜测交互不得进入正式还原。
4. 对每个可见对象和交互路径建立清单，标注稳定 ID、语义、层级、输入、前置状态、状态迁移、反馈、时序、失败路径、现有资源、文本/代码绘制方式及“保留、重构、新生成、删除”结论。

## 双基线门禁

1. 由制作策划和玩法在 `docs/GDD.md`、`docs/TDD.md` 建立参考功能契约，逐项记录前置状态、玩家输入、规则、状态迁移、时序、动画/音效反馈、成功/失败结果、异常与恢复、适配行为及参考证据。证据不足的条目标为“待人工定义”，不得进入实现。
2. 由美术对照 `docs/visual-design.md` 建立参考视觉基线，整理信息层级、构图、角色、场景、UI、图标、字体、色彩、光影、动画、特效和各状态差异。全局规则未冻结时先提交决策包，不得批量生成。
3. 将对象稳定 ID 同时关联参考功能契约、固定视口基准图和资源槽，明确必须一致的行为与视觉、允许变化项及验收容差。视觉优化不得改变已批准功能，功能修复也不得绕过视觉确认。
4. A1 使用低保真实现复现完整可观察功能，包括输入、导航、规则、状态迁移、时序、反馈、成功/失败、重开和受影响异常路径；人工确认功能路径、信息结构和交互边界后才能冻结 A1。只还原布局不视为 A1 通过。
5. 选择至少一个代表性场景和关键状态制作目标效果图或局部样张，在 `docs/visual-design.md` 记录输入、问题、处置、功能契约、目标规格和验收状态；在资源登记记录来源或生成方式、提示词/模型/人工编辑摘要、版本、授权和发布资格。
6. 审查目标效果图与参考功能契约、玩法可读性、触控、安全区、性能预算和全局视觉规则是否一致。功能基线与视觉基线均通过后，才可批量生成、拆分或替换正式资源。

## 生成、人工确认与修改

1. 存在可见场景时，先按 `full-bleed-background.md` 生成并确认无交互满幅背景，再处理角色、前景、UI 或特效。复用符合视觉基线且验证有效的现有资源；其余对象按还原清单生成或人工重绘。生成提示与编辑要求必须引用已冻结规则、对象用途、镜头、目标尺寸、透明背景或可平铺要求，避免仅使用“更好看”等不可验收描述。
2. 每轮生成或重绘完成后，保存带版本号的预览和生成记录，标为“待人工确认”，并向总控提交确认包：预览、适用对象、对应功能状态、与视觉基线的对应关系、已知偏差，以及“确认使用、按意见修改、拒绝并重定方向”三种处置。相关且同批的资源可合并确认，但不得用代表性样张的批准替代后续正式产物确认。
3. 等待人工明确确认。选择修改时记录具体意见，生成新版本并重新提交确认；选择拒绝或改变视觉方向时保留旧版本为“已拒绝”，退回视觉基线或双基线门禁。未得到明确确认的产物不得拆分、替换正式资源、进入候选构建或标为可交付。
4. 不得静默覆盖原始输入、已批准基准画面或上一轮产物；只有新版本获人工确认后，才将上一有效版本标为“已取代”。

## 拆分与接入

1. 人工确认后的合成效果图继续执行 `effect-image-splitting.md` 的查重、拆分方案审查、拆图、逐图检查和 Phaser 验证流程。需要代码绘制的简单几何、遮罩、进度条或动态文本应保留为代码实现，不强制烘焙成图片。
2. 由玩法逐项装配已确认资源，保持稳定 ID、纹理键、锚点、九宫格、布局、输入与状态映射可审计；如需改变参考功能契约、玩法结构或交互语义，退回制作策划和模块门禁重新批准。
3. 接入或运行验证暴露出视觉问题时返回对应美术门；暴露出功能差异时返回 A1、GDD/TDD 或模块门禁。不得以技术修复名义绕过任一确认。

## 对比验收

1. 在与输入一致的视口、设备像素比、前置状态和操作轨迹下运行还原版本，逐检查点捕获截图或录屏，形成参考输入、目标基准、还原结果三方对比；代码输入同时记录复现命令和提交或变更文件。
2. 视觉验收检查构图与信息层级、风格一致性、文字可读性、触控区域、关键反馈、不同宽高比裁切、动画状态、采样边缘、纹理预算和加载性能；所有偏差必须有位置、影响和批准结论。
3. 功能验收逐项重放参考功能契约，核对输入响应、状态迁移、规则结果、时序、动画/音效反馈、成功/失败、重开、异常恢复和适配行为；使用契约测试、集成测试或可复现录屏证明结果。
4. 不以单张静态截图代替运行验证，也不以功能测试通过代替视觉对比。至少覆盖默认、交互反馈、成功、失败、弹窗和受影响异常状态，并在一个目标设备或渠道运行。
5. 只有批准范围内的功能契约全部通过、逐状态视觉对比通过、清单全部有处置结论、生成/重绘产物均获人工确认、正式资源可追溯、Phaser 场景验证通过且无未批准结构或行为变化时，才将本次视觉与功能还原标为“已验收”。证据缺口必须在实现前补证、由人工定义或从批准范围中明确排除，不得在验收时用豁免代替还原。
