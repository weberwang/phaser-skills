# F0-F4 审核漏斗

本文件是风险等级、F0-F4、候选身份、F2 返回结构和 `review.md` 生命周期的唯一权威定义。工作通道决定交付范围，风险等级决定验证与独立审核深度，V0 决定视觉生产路径；三者不得互相替代。所有等级默认单写者、普通分支、顺序执行。

## 审核职责

| 层 | 执行者 | 行为 | 输出 |
| --- | --- | --- | --- |
| F0 实际验证 | 实现者或作者 | 实际执行当前任务适用的项目原生分析、构建、测试、审计、迁移或回归命令，形成候选 | 命令证据、候选身份、变更摘要 |
| F1 分诊 | 总控 | 核对候选身份、范围、风险、验收追踪和证据，选择最小必要 F2 通道 | 必需 F2 通道及理由，或退回实现 |
| F2 只读审核 | 独立非作者 | 只读同一候选，在指定专业维度检查事实；互不依赖的通道可并行 | 结构化结论，不写共享文件 |
| F3 收敛 | 总控 | 确认必需结论覆盖同一有效候选、阻断关闭且集成条件满足 | 批准、退回或阻塞 |
| F4 人工 | 用户 | 只决定无法由事实或专业规则关闭的受保护事项，以及规定的 Phaser 视觉/发布例外 | 候选相关决定绑定当前候选；候选前决定绑定决策 ID/权威工件版本 |

F0 不是命令计划或状态字段，必须实际执行当前任务适用的项目原生命令；没有迁移、审计或特定平台变化时不为形式运行无关命令。F1 只分诊，不代替专业审核。每个风险等级都执行 F0→F1→F3；F3 可以是轻量自检收敛，但不能省略，也不重做 F2。技术缺陷、缺证、未完成项和可判定的专业问题不得进入候选相关 F4。

## 候选身份

F0 通过后冻结候选。代码候选记录基线 Git SHA、候选 Git SHA、diff 范围和命令证据；尚未提交的设计或视觉工件记录候选 ID、每个工件的 `sha256:<64 位小写十六进制>`，并绑定基线或代码 SHA。候选审核、视觉确认和风险接受只能覆盖所记录的候选；候选形成前的阻断决定不虚构候选身份，而是绑定决策 ID、权威工件版本和失效条件。

## 候选修订与重提

修复或“修改后重提”必须保留旧记录并产生新 SHA、候选 ID 或工件哈希，重跑受影响的 F0/F1，重开覆盖事实变化的 F2，并重新执行 F3；只有完成这些步骤后才能重提候选相关 F4。总控只让覆盖事实已变化的旧 F2/F4 结论失效，未受影响的结论可继续引用。沉默、继续工作、旧候选批准、参考输入或其他阶段结论均不是当前候选通过证据。

## 风险等级与 F2 通道

| 风险 | 典型范围 | F2 最小要求 |
| --- | --- | --- |
| `light` | 文档、小修复、确定性配置调整 | 通常无；总控在 F1 后直接做轻量 F3 |
| `standard` | 边界明确的功能或单模块改动 | 行为或验收变化至少启用 QA；其他按变化触发 |
| `high` | 共享架构、跨模块契约、存档、支付、迁移、复杂视觉或难回滚变更 | QA，加上导致升级的玩法、技术、视觉或 Release 通道 |
| `release` | 签名、分发、生产环境、完整平台矩阵或服务部署/回滚 | QA、技术、Release 必审；玩法和视觉按变化触发 |

不可逆外部修改、敏感数据、安全边界、破坏性 API 版本、数据迁移、共享生成文件或难回滚部署至少为 `high`。风险只决定证据与审核深度，不决定并行、worktree 或是否创建流程状态。V2a/V2b 独立美术审核、适用 V1/V2 用户确认不得被任何风险等级降级跳过。

API 契约/版本、认证授权、幂等/重试/超时、数据迁移/回滚、服务端测试、部署监控、备份恢复或客户端兼容变化触发技术通道；生产或发布变化同时触发 Release。服务端不在范围时，只审核已记录的外部依赖、所有者和客户端边界。

## F2 返回结构

```text
审核通道：玩法 / QA / 技术 / 视觉 / Release
审阅者：
候选 SHA 或候选 ID/工件哈希：
覆盖范围与事实：
使用证据：
发现：
- [Critical|Important|Minor] 文件、工件或具体区域 — 问题
缺失证据：
开放问题：
结论：approved / changes_requested / blocked
```

视觉通道另给出明确的专业审美结论。`Critical/Important/Minor` 是 F2 审核发现的处理优先级，只用于决定审核是否退回；发现进入正式缺陷跟踪后，再依据当前候选的可观察影响映射为本文件定义的 P0-P3，二者不得直接互换或混用。任何 Critical、未解决 Important、必需证据缺失或 `changes_requested` 都退回作者。作者自检属于 F0，不能冒充 F2；F2 审阅者不得修改候选或共享 `review.md`。

## `review.md` 生命周期与单写者

仅在风险或交接需要持久独立验收时创建 `docs/tasks/<task-id>/review.md`，且总控是从创建到关闭的唯一写入者：

1. F0 后记录候选身份、基线、diff 范围和命令证据引用。
2. F1 后记录风险、变化维度、必需通道、触发理由和派发或退回结论。
3. F2 返回后记录审阅者、时间、候选身份、覆盖事实、证据、发现和原始结论位置；审阅者不并行写本文件。
4. 新候选保留历史，明确因覆盖事实变化而失效及继续有效的通道。
5. F3 关闭时列出有效通道、已关闭阻断、集成/CI 事实和最终结论。

`review.md` 只留存决策、证据和结论，不驱动状态机、自动合并、分支或 worktree 清理。

## 视觉 V0-V5 映射

所有视觉候选先执行通用 F0/F1，再按 V0 路径选择生产与审核落点；不得给每个 V 阶段机械叠加一套 F0-F3。

| V0 类型 | 生产路径 | 必需专业审核与收敛 |
| --- | --- | --- |
| 原子资源 | 引用仍适用、有效且绑定当前范围的 V1 契约、两类确认、视觉可交付、冻结基线与预算，走 V3→V4→V5 | V4 独立美术/资源 F2；V5 提交动态集成证据，按风险完成 F3；任一引用失效即升级路径 |
| 组件/资源集 | 走 V1→V5；结构、布局、交互、状态集合或资源槽变化时执行 V1 确认；高保真形态变化时执行 V2 | V2a/V2b 独立美术、V4 资源审核及风险触发通道；V5 后 F3 |
| 场景/整套 UI/视觉系统/参考还原及重做类任务 | 完整 V1→V5，两道确认均强制 | V2a/V2b、V3/V4 的适用专业通道；V5 后 F3 |

V2a/V2b 和跨资源一致性必须由独立非作者美术审核。总控只能核对流程、候选绑定和证据完整性；缺独立美术时标记“专业视觉未验证”并阻断下游。明显审美缺陷、游戏感缺失、开发口径残留或缺证先退回最早受影响阶段，不能送给用户兜底。

### V1 低保真确认

顺序为 `V1 契约/草图或灰盒 → 适用 F0 → 冻结候选身份 → F1 → 必需 F2 → F3 → F4 用户确认 → V2`。确认只覆盖信息结构、构图、层级、资源槽、关键状态、交互区、输入流程、布局几何、安全区/响应式意图、失败/恢复和排除项，不批准视觉风格、材质、光影、正式资源质量或最终游戏感。

确认包至少包含确认 ID、候选 SHA 或候选 ID/工件哈希、绑定基线/代码 SHA、范围、契约版本、草图或灰盒路径、关键状态、结构/交互/布局意图、排除项、待 V2 变量、已关闭问题和返工影响。用户结论只允许“通过”“修改后重提”或“拒绝”。修改后按“候选修订与重提”执行；拒绝按根因回到 V1、制作契约/GDD，或重新完成受影响的模块审计，只有仍存在受保护架构取舍时才进入 grilling/F4。

### V2 高保真确认

顺序为 `V2a 方向基准 → V2b 整体视觉审阅与动态可玩样片 → 适用 F0 → 冻结候选身份 → F1 → 独立美术及其他必需 F2 → F3 → F4 用户确认 → V3`。确认包至少包含确认 ID、候选身份、范围、全局基线 ID/版本/风格指纹、代表性效果图和关键状态、动态证据、差异、独立美术结论、已关闭问题、V3 范围和返工影响。

只有当前候选明确“通过”才能形成绑定确认 ID 的视觉可交付结论。修改后按“候选修订与重提”执行；拒绝按根因退 V2a 或 V1。低保真确认不能替代高保真确认，任何确认也不能替代动态样片、独立美术审核或缺陷修复。

## 平台证据

- 共享基础完成后，以代表性 Vite/Phaser 启动、Boot/首场景、路由、资源加载和适用插件烟测证明基础可用。
- 关键玩法流完成后，在主目标平台运行核心循环、失败/恢复和场景切换烟测，只证明该流与该平台。
- 只有最终集成、G3 或发布阶段执行完整渠道/平台、方向、视口、性能、存档与合规矩阵，才能形成平台全量结论。
- 不得从单任务构建、截图或局部烟测宣称全平台通过；不得自动发起真机验收。

## P0-P3 缺陷优先级唯一标准

本节是 P0-P3 的唯一权威定义，按当前候选的可观察影响而非修复难度判定。

| 级别 | 判定标准 | 关闭条件 |
| --- | --- | --- |
| P0 | 无法启动、不可恢复的数据丢失/损坏、合规或安全硬阻断，或核心流程不可完成 | 修复并在受影响环境复验；G2 前未关闭项须有绑定当前候选的 F4 豁免 |
| P1 | 关键体验、关键功能或目标渠道不可接受，但不满足 P0 | 修复并针对性回归；G2 前关闭或取得绑定当前候选的 F4 豁免 |
| P2 | 有可行绕过方式且不阻断核心流程和目标渠道 | 修复并回归，或记录负责人、计划质量门和影响范围 |
| P3 | 不影响正确性、核心体验或发布可用性的优化项 | 完成，或明确纳入/拒绝并记录理由 |

P0/P1 豁免记录必须包含缺陷 ID、候选身份、影响、证据、补偿措施、负责人、失效条件和人工结论；排期、“已知问题”或沉默不是豁免。

## 集成边界

F3 批准不自动合并。合并前总控仍须检查当前分支、批准候选 SHA、干净工作区、`git diff --check`、必需测试/CI、审核结论和用户授权，并通过标准 Git/PR/CI 集成。只读探索和审核可并行；并行写入或 worktree 必须用户明确要求，写范围互斥。不得创建 YAML/JSON 流程状态、自动 finalizer、自动合并或自动清理。
