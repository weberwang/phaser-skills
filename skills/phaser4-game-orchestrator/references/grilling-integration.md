# 拷问与 F4 集成

总控先从代码、配置、现有权威工件和确定性执行确认事实。实质用户取舍调用 `$grilling` 并绑定 Work Item、prompt/context 与 baselineHash；首次模块或边界变化强制模块门和 grilling。F4 只在 F3 后处理精确集成/发布决定。

## 一般触发边界

1. 候选形成前先区分可探索事实与阻断候选的用户决定。前者继续探索；后者可直接 grilling，记录决策 ID、权威工件版本、范围、理由和失效条件，不虚构候选 SHA。
2. F0 处理授权与流程合规，F1 处理规格一致性，F2 处理专业质量，F3 处理工程验证，F4 处理精确集成/发布决定；首次模块或边界变化强制完成 grilling。
3. 新模块和模块边界变化仍按风险/变化执行模块审计、技术和 QA F2；若候选形成被实质架构决定阻断，可按第 1 条先 grilling；已有候选时则按第 2 条执行。证据完整且无用户决定时直接继续。
4. 未获结论前只冻结直接受影响范围，无依赖工作继续。结论绑定当前候选身份；修订候选只让覆盖事实变化的决定失效。

## Phaser 明确 F4 例外

- 适用 V1 的当前低保真候选用户确认。
- 适用 V2 的当前高保真候选用户确认。
- G3 外部发布放行，以及明确的 P0/P1 或其他受保护风险接受。

V1/V2 对象确认不是开放式 grilling，也不是可扩展的 F4。低保真只确认结构/交互/布局意图；高保真另行确认当前视觉候选。两者都写入 Approval Ledger 的当前明确下一门，不能授权正式资源或豁免缺证、技术与专业缺陷。

## 记录

候选前决定记录决策 ID、权威工件版本、问题、影响、依据、推荐、人工结论、日期和失效条件；候选相关决定改为绑定候选身份。V1/V2 分别使用专用确认记录。旧候选批准、沉默、继续工作、参考输入或其他阶段批准均无效。控制面仅索引决定，详细事实留在各自权威交付物。
