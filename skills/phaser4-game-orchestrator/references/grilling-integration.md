# 拷问与 F4 集成

总控先从代码、配置、现有权威工件和确定性执行确认事实。若无法确定的实质性范围、优先级、取舍、风险、验收、依赖、视觉方向或不可逆架构决定会阻断候选形成，可以在候选前调用 `$grilling`，并把决定绑定决策 ID 与当时的权威工件版本。已有候选的相关 F4 则必须在 F3 后进入。不得仅因新阶段、新页面、新模块或模块边界变化重复提问。

## 一般触发边界

1. 候选形成前先区分可探索事实与阻断候选的用户决定。前者继续探索；后者可直接 grilling，记录决策 ID、权威工件版本、范围、理由和失效条件，不虚构候选 SHA。
2. 已有候选时由 F1 区分事实缺口、专业问题和用户取舍：事实缺口退 F0，专业问题进入对应 F2；候选相关用户取舍必须等 F3 收敛后进入 F4。
3. 新模块和模块边界变化仍按风险/变化执行模块审计、技术和 QA F2；若候选形成被实质架构决定阻断，可按第 1 条先 grilling；已有候选时则按第 2 条执行。证据完整且无用户决定时直接继续。
4. 未获结论前只冻结直接受影响范围，无依赖工作继续。结论绑定当前候选身份；修订候选只让覆盖事实变化的决定失效。

## Phaser 明确 F4 例外

- 适用 V1 的当前低保真候选用户确认。
- 适用 V2 的当前高保真候选用户确认。
- G3 外部发布放行，以及明确的 P0/P1 或其他受保护风险接受。

V1/V2 确认不是开放式 grilling。总控只能提交已关闭可判定缺陷、完成适用 F0、冻结候选身份、完成 F1、必需 F2 和 F3 的受保护确认包。低保真只确认结构/交互/布局意图；高保真另行确认当前视觉候选。两者不能互相替代，也不能豁免缺证、技术问题、专业审美缺陷或动态样片。

## 记录

候选前决定记录决策 ID、权威工件版本、问题、影响、依据、推荐、人工结论、日期和失效条件；候选相关决定改为绑定候选身份。V1/V2 分别使用专用确认记录。旧候选批准、沉默、继续工作、参考输入或其他阶段批准均无效。控制面仅索引决定，详细事实留在各自权威交付物。
