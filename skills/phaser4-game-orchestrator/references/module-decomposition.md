# 模块划分与实现前拷问

新建模块、首次实现模块，或改动会改变既有模块职责、公开契约、状态所有权或依赖方向时，完整读取本文件。模块划分不是按文件夹或类名分组，而是冻结可独立说明、实现、测试和替换的职责边界。

## 划分模块

1. 从已批准的 GDD 增量提取玩家行为、状态变化、平台能力、资源依赖、失败路径和验收证据；盘点代码库已有职责，优先扩展边界清晰的现有模块，不为单个函数、类型、配置或图片创建伪模块。
2. 建立候选模块图。每个模块只承担一类业务责任，并记录：职责与非目标、入口、公开输入/输出、拥有的状态和数据、生命周期、错误与降级、资源/平台依赖、允许依赖、禁止依赖、测试边界和负责人。
3. 规定单向依赖和调用契约。共享能力只有被两个以上已批准模块稳定复用时才提取；不得创建无边界的 `common`、`utils`、全局事件或可被任意写入的共享状态。循环依赖、双向状态写入和绕过公开入口的访问必须在拷问前消除或列为待决策。
4. 给出实现顺序：先契约与纯规则，再适配层和表现，最后跨模块集成；每一步必须能独立验证。并行实现只分配没有文件所有权冲突、接口已经冻结的模块。

## 强制拷问门禁

1. 在编写生产代码、搭建模块骨架、创建迁移或接入正式资源前，把候选模块图交给总控。只读调查、复现和用于形成方案的短期实验可以继续，但实验产物不得进入正式实现。
2. 总控必须调用 `$grilling`，即使现有文档看似完整也不得跳过。拷问至少确认模块是否需要存在、职责与非目标、状态所有权、公开契约、依赖方向、失败边界、实现顺序和验收证据；低风险且相互独立的模块可组成一个确认包，高影响或相互依赖的边界逐项确认。
3. 人工可以“批准”“要求修改”或“拒绝/合并模块”。要求修改时修订候选模块图并重新拷问；不得把沉默、对功能范围的批准或对旧模块的批准视为当前模块边界获批。
4. 人工批准后，由技术架构在 `docs/TDD.md` 写入模块清单、依赖矩阵和确认记录，并由总控在控制面写入结论索引；模块状态标为“已批准待实现”。只有该状态的模块可以进入实现。

## 变更与验收

1. 实现发现需要新增模块，或需要改变职责、公开契约、状态所有权、依赖方向、持久化/平台边界时，停止直接受影响的实现，更新候选模块图并重新执行拷问。模块内部不改变批准边界的低风险实现细节无需重复拷问。
2. 逐模块验证公开契约、状态只有单一写入所有者、禁止依赖未出现、错误不会跨边界静默吞掉，并用契约测试或可复现集成证据证明依赖方向。
3. 模块只有在边界与实现一致、测试通过、下游只通过公开入口使用、文档记录实际路径且没有未批准依赖时，才可标为“已实现”。
