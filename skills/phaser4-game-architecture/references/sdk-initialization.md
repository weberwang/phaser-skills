# SDK 统一初始化

游戏项目所有实际采用的 SDK 都通过 `src/bootstrap/initialize-sdks.ts` 统一初始化。`src/main.ts` 负责应用装配，只调用该文件的唯一入口 `initializeSdks`；SDK 的启动调用、先后依赖、可并行分支、延迟触发条件和失败处理入口集中在此文件维护，不散布到 Boot/Preload、Scene、UI、业务服务构造函数或模块导入副作用中。没有使用 SDK 时不创建占位文件或安装额外依赖。

## 文件职责

- 统一文件读取已注入的平台能力、分环境配置和服务接口，只编排当前已启用且平台支持的 SDK；公开类型继续放 `game/contracts/`，原生调用、事件转换和平台细节继续由 `platform/` 的适配器封装。初始化编排可以调用适配器的初始化接口，但适配器不得自行在构造或导入时启动 SDK。
- 所有显式 SDK 初始化的发起点在本文件；业务层只调用已装配服务或发出业务事件，不直接 import 第三方插件、调用 initialize，或在场景重进时重新启动 SDK。原生宿主必须早于 JavaScript 执行的自动初始化无法移到 TypeScript 时，在本文件和 TDD 登记真实宿主前置及其验证位置，不另建第二个业务初始化入口，也不重复调用原生初始化。
- 第三方 SDK 已由上层插件或聚合 SDK 管理的传递依赖只登记依赖关系，不再次手动初始化。单文件统一的是应用层初始化编排，不把第三方实现、平台桥接、运行期广告加载、业务逻辑或所有回调搬进同一个文件。
- 采用明确的函数与分支表达当前项目顺序，不为此引入通用启动框架或自动拓扑调度器。统一文件归属共享装配入口，按 `SHARED` 串行修改；各 SDK 适配器仍按模块职责归属，遵守单文件规模和中文注释规则。

## 顺序与依赖

在 TDD 为每个实际采用的 SDK 写明：平台与环境开关、配置来源、适配器、宿主/桥接/其他 SDK 的真实前置、真实就绪判据、并行或延迟触发条件、是否阻塞核心启动、失败降级和重试所有者。初始化文件与该表保持一致，不把所有 SDK 机械排成串行链，也不无条件并发。

1. 先取得当前 SDK 所需的配置、宿主/桥接及基础服务。仅等待真实前置，按项目依赖确定顺序；不存在依赖的分支可并行。缺失必需前置时不调用依赖它的 SDK，并返回真实失败或未就绪结果。
2. 下游需要的是初始化完成，就等待官方完成回调或明确就绪状态，不能把“请求受理”、超时或某个隐私结果当作 SDK 已就绪。SDK 初始化、账号登录、广告加载等状态分别记录。
3. 只有 TDD 明确为核心运行必需的 SDK 才能阻塞核心启动。广告等可选能力独立推进，统一入口应提供核心就绪与各 SDK 后台结果的区分，不能因等待全部可选 SDK 而阻塞 Phaser。调用与返回形式按项目公开契约定义，不以 `Promise.all` 等待整个可选集合后才启动游戏。
4. 登录完成、用户操作或宿主条件恢复后才允许启动的 SDK，其触发和后续调度仍归本文件；业务只发布条件变化。平台不支持、功能禁用、依赖失败、等待条件和真实初始化失败需要可区分，不以空实现伪装成功。

## 幂等、失败与生命周期

- 同一应用生命周期、同一有效配置只发起一次初始化，重复调用复用进行中的任务或已完成结果；场景切换不重建 SDK。配置切换或销毁需让旧回调失效，并清理本文件创建的监听器。
- 每个 SDK 的初始化失败只影响真实依赖它的分支。记录实际错误、超时与未完成项，不吞掉错误后返回统一成功，也不把一个可选 SDK 的失败传播到无关核心流程。
- 本文件是初始化启动和恢复的唯一编排入口；若 SDK 领域服务已有唯一重试任务，由本文件接入并消费其状态，不另建重复 timer 或重试循环。SDK 特有的退避、宿主恢复、销毁与回调幂等由对应适配器/领域服务按合同维护，不与广告加载等运行期任务混用。

## 广告与隐私分支

MAX 与 CMP/Google UMP/ATT 的初始化或收集入口均由本文件统一调度，但保持[广告合同的独立推进关系](../../phaser4-game-ad-integration/references/applovin-max-contract.md#初始化与隐私独立推进)：隐私任务不成为 MAX 初始化或初始化恢复的前置；MAX 初始化成功也不代表可以请求广告。隐私真实状态已传递且请求策略满足后，才由广告服务执行允许的加载/展示；Banner 不参与启动预加载。

MAX 内建 Terms and Privacy Policy Flow 必须在 MAX 初始化前显式关闭，并核对同步后 Android/iOS 实际构建配置；关闭的是内建交互流程，广告服务开关和 MAX 初始化调用仍保持启用。MAX 的真实初始化完成回调、失败重试和广告请求隐私门分别维护，不把“配置已关闭”写成“SDK 初始化成功”。原生配置、调用与验收见[关闭 MAX 内建流程](../../phaser4-game-ad-integration/references/applovin-max-contract.md#关闭-max-内建隐私流程并保留初始化)。

### AppsFlyer 独立启动

项目采用 AppsFlyer 时，在 `initialize-sdks.ts` 中登记独立启动分支，通过项目选定的平台适配器调用其初始化与启动接口。它只依赖自身真实平台、配置、宿主和适用隐私条件，不等待 MAX 初始化、MAX 内建隐私弹窗、广告加载或 MAX 的成功/失败回调；MAX 也不等待 AppsFlyer 的初始化、启动或归因回调。不得把 AppsFlyer 启动放入 MAX 初始化回调、MAX 失败兜底或 MAX 内建隐私流程完成回调中。

两者各自维护配置、状态、操作身份、失败与恢复任务；任一失败、超时或暂不可用都不取消另一分支，也不因可选 SDK 等待阻塞 Phaser。适配器按锁定插件的官方语义区分“初始化受理”“允许启动”“启动结果”和异步归因结果，不能把暂未收到归因回调当作启动失败。若 AppsFlyer 自身采用 ATT 等等待机制，保持其独立有界策略，不转化为 MAX 的前置依赖，也不重复发起系统授权。项目未采用 AppsFlyer 时不因本规则额外安装。

选用 AppsFlyer 插件时核实其实际版本和 Capacitor 支持，不将其他框架或不同主版本的 API 混用；若采用[官方 Cordova 插件](https://github.com/AppsFlyerSDK/appsflyer-cordova-plugin)，其官方兼容性说明仍须逐项验证。采用手动启动模式时，必须在自身前置满足后调用锁定版本对应的 start 接口，不能只完成 init 就遗漏启动；自动启动模式则不重复 start。两种模式都不依赖 MAX 回调。

既有广告合同已标记官方接入顺序与解耦目标的能力冲突。统一文件只集中编排，不消除该冲突；仍须核对锁定版本的官方能力与适用集成证据。不能改写依赖、伪造初始化完成或另建原生桥以宣称满足合同。MAX adapter 与其管理的聚合网络 SDK 不再逐个由业务初始化。

## 交付与验证

基础阶段交付实际需要的统一初始化文件、适配器公开契约和 TDD 初始化表；具体 SDK 的新增仍需当前需求与能力档支持，不因为预留启动位置安装未采用 SDK。初始化编排不包含正式场景玩法或视觉资源消费，仍遵守 foundation-only 与场景阶段边界。

按当前改动推荐并自动执行适用 T0–T3 验证。实现时定向检查重复启动、真实依赖等待、无依赖并行、可选失败不阻塞核心、延迟条件恢复、平台不支持、旧回调失效及已有恢复任务不被重复创建；核对 SDK 初始化没有散落在 Scene、构造函数或导入副作用中。只交付本工作流规范时检查链接、模板输出与现有回归，不把文档检查描述为真实 SDK 集成通过，不自动发起真机或外部配置操作。

采用 MAX 与 AppsFlyer 时，额外覆盖两种完成先后顺序、任一失败/超时、隐私仍未决以及重复启动：MAX 内建流程关闭后仍发起且只发起一次有效初始化，AppsFlyer 不依赖其结果；各自真实回调只更新自身状态。目标项目必须提供实际有效原生配置和适用初始化/启动证据，才能报告运行通过。
