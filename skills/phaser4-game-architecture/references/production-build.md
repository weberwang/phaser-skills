# 生产构建压缩与发布检查

新建或调整 Phaser 游戏的 Vite 生产构建、准备发布候选时读取本文件。采用 [Phaser 官方 Vite 模板的生产配置](https://github.com/phaserjs/template-vite/blob/main/vite/config.prod.mjs)作为本工作流的基础压缩要求；这是构建期压缩，不是完整的反编译加固。

## 配置接入

先检查目标游戏的 `package.json` 构建脚本及其实际加载的 Vite 配置。将以下 `build` 字段合入该生产入口（例如 `vite/config.prod.mjs` 或 `vite.config.ts`），保留现有插件、入口、分包和资源配置，不新建未被构建命令引用的配置文件。

```js
build: {
    // 生产包不生成源码映射，避免随公开产物泄露源码；开发调试配置独立维护。
    sourcemap: false,
    minify: 'terser',
    terserOptions: {
        // 两轮压缩与官方模板一致；不额外开启属性名混淆，避免破坏动态访问和外部接口。
        compress: { passes: 2 },
        mangle: true,
        format: { comments: false }
    }
}
```

- `minify: 'terser'` 显式选用 Terser；`passes: 2` 执行两轮压缩，`mangle: true` 缩短可改名标识符，`comments: false` 移除生成代码中的注释。
- 在目标游戏已有包管理器下将 `terser` 声明为开发依赖，并同步锁文件；npm 项目可执行 `npm install -D terser`。已经声明时复用，不安装到技能包根目录，也不依赖传递依赖碰巧存在。
- 配置作用于生产构建；开发服务器沿用原开发配置。单文件配置应将选项放入 `build`，不另加运行时混淆代码。
- 保留第三方依赖要求随包分发的许可证或 NOTICE 文件；删除代码注释不能代替授权材料交付。
- 这组配置不包含字符串编码、控制流混淆、反调试或防篡改；需要时按用户要求另行实施，不能声称仅配置 Terser 就已实现这些能力。

## 生产 Source Map

- 生产入口显式设置 `build.sourcemap: false`，并核对 CLI 参数、插件、渠道配置与打包后处理没有重新启用映射或复制旧映射；开发环境仍可按需使用 Source Map。[Vite 官方说明](https://vite.dev/config/build-options.html#build-sourcemap)中的 `hidden` 仍生成映射文件，不满足默认关闭要求。
- 发布前检查最终公开目录与实际渠道包中的 Web 资源，包括 JS/CSS、Worker、第三方或自定义引擎文件：不得包含 Source Map 文件（通常为 `*.map`，包括预压缩副本）、内联 Source Map、`sourceMappingURL` 指令或指向映射的响应头。不能仅因配置为 `false` 就判定发布检查通过。
- 将检查对象、方法、结果和阻断项写入发布清单；发现映射时追溯生成或复制来源，修正后重新构建并复查最终候选，不只删除当前目录的单个文件。历史部署/CDN 上的旧映射也需在可只读检查时核对；外部删除另按已有操作授权执行。
- 仅在用户明确要求生产排错映射时采用独立私有工件流程，记录理由、存储位置和访问范围；映射不得进入 `public/`、公开发布包或公开 CDN。涉及外部上传仍按精确对象与已有授权执行。

## Phaser Compressor 引擎裁剪

[Phaser Compressor](https://phaser.io/news/2024/05/phaser-compressor-released)通过 Web 界面选择引擎组件、目标浏览器与导出格式，生成较小的自定义 Phaser 引擎包。它用于包体优化，不处理业务代码加密或反编译保护。

1. 将 Compressor 纳入生产构建评估，先核实工具当前支持的 Phaser 精确版本、所需功能、导出格式和访问资格。官方早期介绍针对 Phaser 3，不能据此断言支持当前 Phaser 4；不支持、无访问资格或没有实测收益时，明确记录未采用原因，沿用项目现有引擎构建，不降级 Phaser 或自动购买订阅。
2. 依据实际场景、插件和运行时动态创建对象整理保留/移除清单，只裁剪已确认未使用的能力。保存可导出的配置；无法导出时记录可重建的完整选项，以及 Phaser 版本、生成方式、浏览器目标、导出格式和产物路径。
3. 将自定义引擎接入项目实际解析入口，统一业务、插件与构建器的 Phaser 引用；核对最终依赖图和产物，避免自定义引擎与 npm/CDN 完整引擎同时加载。同步核对类型声明对应版本、必要许可证和 Source Map 检查。
4. 使用相同游戏代码、资源、压缩方式和渠道条件对比裁剪前后的引擎及完整发布包体积，记录原始与实际采用的传输压缩口径。验证启动、场景切换及保留的物理、加载器、渲染和插件路径；缺模块、运行错误或无收益时调整裁剪方案，不用官方宣传比例替代测量。
5. 发布清单登记采用状态、版本、配置位置、实际入口、体积对比和功能验证结果；Phaser、插件或功能清单变化时重新评估并生成受影响候选。

## 验证与发布交接

1. 核对实际构建脚本引用的配置及合并、渠道覆盖结果，确认上述选项最终生效，并记录配置路径与命令。
2. 按项目现有入口执行相关类型检查和生产构建（例如已有的 `npm run typecheck`、`npm run build`），检查退出状态和最终产物；执行上述 Source Map 发布检查及 Compressor 适用性/采用结果核对。未声明的检查脚本不凭空调用。
3. 在生成的生产包上定向验证启动、场景切换、资源加载和依赖动态名称的接口；复用已有健康预览实例，需要新建时先检查可复用进程。视觉显示仍由用户人工检查，不自动发起真机验收。
4. 在 TDD 与发布清单记录依赖、最终选项、构建结果及未覆盖项；构建成功不等于运行烟测或完整平台矩阵通过。
