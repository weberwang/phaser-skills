# 功能语义分组约束

适用于 V2 的效果图拆解与后置布局。先确认功能归属，再分别记录实际父级和定位参照。父子关系表达功能、共同状态、交互、生命周期或真实布局管理职责，定位参照表达位置计算依据；位置依赖本身不要求更改父级。不得根据元素类型、距离或最小包含矩形自动确定父级。

屏幕节点还须记录父容器职责、布局所有者、尺寸/溢出/安全区和输入策略。字段及 Phaser 根节点、空容器与 V1/V2/V3/V4 组织规则详见[Phaser UI 节点组织](layout-hierarchy.md)；`ui_layout` 不取代本文件定义的语义归属。

## 判断原则

- 全屏 UI 以场景逻辑尺寸为根参照；有底板弹窗以底板对应功能容器的尺寸为内容参照，底板容器本身相对场景定位；无底板弹窗以宿主场景逻辑尺寸为参照。先按[场景与弹窗尺寸参照](layout-hierarchy.md#场景与弹窗尺寸参照)确认边界，再建立内部位置依赖与信息分组；弹窗底板是功能部件，不是全屏背景。
- `parent_element_id` 表达真实功能或布局父级。可选 `ui_layout.position_reference_id` 独立指定位置参照，省略时使用父级；允许同一 scene/state、同坐标空间的兄弟节点（包括叶子）、祖先和稳定根，不允许任意跨分支叶子或全屏装饰背景。独立参照须有 `POSITION` 职责，父边与参照边合并后必须无环。
- 子项突出非根父框时，声明 `ui_layout.visual_overflow: {reason: "关闭按钮突出面板边缘"}`，保留真实父级和父框尺寸。声明只放宽该父框的包含检查，不豁免 viewport、安全区、画布、裁切、输入和可读性要求；没有声明仍检查完整包含，不为通过检查扩大面板或增加无职责包装层。
- 信息分组由表达目标决定：共同表达同一个信息或功能、但彼此没有位置依赖的元素必须归入同一个 `component` 容器，并作为同级子元素列出，不能任选其中一个充当另一个的父级。按钮的底板、图标、标题可以是独立元素，但应在同一信息组内。
- 同时存在信息归属和位置依赖时，两项都要保留。例如按钮图标与文字同属按钮 Container，文字可参照图标定位，不将文字改挂到图标下。Phaser 的功能 Container 与底板图片保持各自身份；不照搬 Cocos 的 Sprite 组件与 Node 共存模型，也不把底板图片尺寸当作 Container 的自动布局尺寸。
- 区域容器组织多个功能组件。例如侧栏先包含多个入口组件，各入口再包含自己的图标与文字；不能把所有入口的图标、文字直接平铺在侧栏下，也不能建立仅按“所有文字”归类的容器。
- 原子资源身份与布局归属分离。不同入口可以复用同一图标资源，但每个可见实例仍属于自己的入口；不能仅凭相同资源 ID 合并容器。
- 不影响功能时，按[完整拆解与视觉显著性](../../phaser4-game-asset-integration/references/asset-production-routes.md#完整拆解与视觉显著性)完整登记合成位图中可分离的文字、图标、底板、色彩填充等部件；系统文本和原生填充也保留为独立拆解项。拆开视觉来源不拆散功能归属，交互、状态联动、动态更新与本地化仍由对应组件协调。
- 几何包含、距离、视觉接近只用于辅助观察与验证。语义归属明确后才验证 bounds、计算偏移；没有声明父级时禁止自动选择最小包含容器。
- 独立标题、背景、装饰或不可可靠分离的完整品牌美术可以直接属于区域或根，不强制创建只有一个元素的容器；完整美术不能成为省略可独立部件的理由，整体保留时记录不可分离或分离会损伤既定视觉意图的原因。无需强制每个组件同时拥有图标、底板和文字。
- 空容器必须有已确认的用途与理由，不得把留白当作空容器。分组不得改变原图构图、元素位置、尺寸或已有元素顺序。

## 拆解记录

每个最终确认的 `decomposition_elements` 元素必须显式声明：

```json
{
  "parent_element_id": "entry-container",
  "semantic_grouping": {
    "kind": "part",
    "rationale": "该文字属于此入口，与入口图标共同移动并保持相对位置"
  }
}
```

`parent_element_id` 只能引用同一 scene/state 的已声明容器，或稳定根 `viewport` / `safe-area`，最终确认不接受缺省父级。`ui_layout.position_reference_id` 省略时为父级；独立参照不改变功能归属。`semantic_grouping.rationale` 说明共同表达的信息、父级职责及必要的独立定位关系，不以“都是文字”“距离最近”作为理由。

| kind | 元素类型 | 归属约束 |
| --- | --- | --- |
| `region` | 容器 | 组织区域、功能组件和独立元素；父级为区域或根 |
| `component` | 容器 | 表示一个功能组件，允许组合子组件或明确的空容器；父级为区域、功能组件或根 |
| `part` | 非容器 | 功能组件中的图标、底板、文字等部件；直接父级必须为 `component` 容器 |
| `standalone` | 非容器 | 有理由独立布局的标题、背景、装饰或整体美术；父级为区域或根 |

这里的 `kind=component` 表示功能组件容器，与拆解元素字段 `element_type=component` 表示非容器元素不是同一概念。复合功能可以嵌套组件，但区域不能塞入功能组件内部。所有显式父关系必须无环、不自指、几何可包含，且空容器标记与实际子项一致。

## 阶段与校验边界

1. 阶段 A 先登记原子元素，再按真实功能归属登记父级、独立定位参照、溢出和理由，生成拆解图与技术 JSON。存在歧义就保留为待补充草案，展示争议点，不自动猜测或伪造人工决定。
2. 拆解人工确认覆盖分组种类、理由与父级。缺少这些声明或结构不合法，不得通过最终确认或进入布局。
3. 阶段 B 按已确认元素原序映射实际父级与有效定位参照，分别生成 `parent_target_bounds` 和 `reference_target_bounds`，再做双轴对齐判断。相对距离按真实父级计算，锚点偏移按有效参照计算；审阅资料同时展示两类关系。
4. 机器检查字段完整、父级类别、参照上下文、合并依赖环、显式溢出、根边界与确认身份一致性。机器不能证明功能语义或理由真实；滥用分组、`standalone` 或溢出声明仍由人工审阅识别，不以 PASS 或 AI 自评代替确认。
5. 新增容器、改变功能归属或分组理由，返回阶段 A 更新提案并重新确认，使旧拆解与布局身份失效。仅调整既有归属下的停靠与偏移，重新走布局确认，不自动重做参考图。

新增节点需要纳入拆解确认，已有元素顺序、身份和原始测量保持不变。布局目标可按明确的[居中策略](center-alignment.md)平移，并传播父级或参照位移；不得回写 proposal 原始 bounds 或确认回执。
