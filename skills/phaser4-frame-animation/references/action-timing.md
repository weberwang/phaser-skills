# 完整动作与时间轴

在灰盒制作前读取本文件。它定义动画任务的制作单位与时间设计；视频提示词、灰盒、抽帧预览和最终接入消费同一份动作计划。

## 动作分组

- 按行为语义确定动画单元：记录触发条件、初态、完整阶段序列、终态或循环周期，以及播放期间需要表达的事件。同一次触发下连续完成的阶段属于同一单元，共享时间轴与完整预览；阶段数量和事件数量不决定视频任务数量。
- 具有独立触发、分支、取消、复用或生命周期的行为可以划为不同单元，记录边界与理由。区分行为单元、运行时动画 key 和源素材包装：多个 key 可以来自同一完整素材，一个素材文件也不能代替行为边界定义。
- 连续单元内部默认整体制作。确需分段生产时，先写明生产理由、各段入姿/出姿、锚点、连接条件与总时间轴，并在灰盒中连续展示组合结果。不得因任务清单分行、事件数量、工具参数或生成器时长限制自行切断行为。

当前抽帧工具每次输出一个覆盖全部输入帧的动画 key。玩法确需多个 key 时，可从已确认的完整视频按运行时边界剪出派生输入，各自抽帧并绑定合同，保留整组来源与连续预览；不要直接缩小报告中的帧范围来冒充工具支持多段动画，也不要因此重新生成多个独立动作视频。

## 游戏时间先于视频时长

先依据行为节奏决定一次播放的总时长或循环周期，再分配各阶段和事件。优先读取已有玩法时序；没有时序时提出明确建议并通过灰盒确认，不套用生成器或示例的固定时长。相邻阶段按行为要求直接过渡，只有计划明确要求时才返回初态、重复准备或保持姿态；各阶段不必等长。

动作计划保存为项目内设计工件，至少包含：

| 信息 | 要求 |
| --- | --- |
| 行为单元与边界 | 名称、触发条件、初态、阶段顺序、终态或循环周期；生产/运行时分段另列原因 |
| 整组时长与 FPS | 游戏总时长（毫秒）、目标 FPS 与预计帧数 |
| 阶段区间 | 每段开始/结束毫秒、运动/过渡/保持意图、关键姿态与连接方式；区间覆盖整组，无未说明空档 |
| 玩法事件 | 事件名称、作用、同一时间轴上的毫秒与目标帧；无事件时明确记录无 |
| 播放与保持 | 单次/循环/终态保持方式；有意定格区间、用途与时长；循环接缝要求 |
| 画布合同 | 视角、朝向、尺寸、锚点、完整运动范围 |
| 视频时间映射 | 源视频时长独立记录；收到视频后补齐有效区间、裁剪与重定时映射 |

预计帧数按游戏时长乘 FPS 计算并记录取整规则，事件映射至可播放帧；量化容差最多一个目标帧间隔，不能丢失关键事件或短促衔接。若当前 FPS 无法表达事件，调整 FPS 或动作设计并交付灰盒确认，不盲目拉长动作。

提示词对每个阶段同时写出时间区间、动作意图、关键事件和到下一阶段的过渡；灰盒按同一时间轴完整播放。只列姿态名称或笼统写“自然流畅”，不能代替阶段之间的时间与连接约束。

## 运动、保持与循环

运动阶段须在计划区间内持续推进；静止保持必须在计划中标注区间与意图，不能因源素材没有后续动作就自动延长。低幅度运动仍属于运动，不能默认定格；单次动画按计划结束或保持终态，不自动循环或添加等待。

循环动画需在灰盒和正式预览中跨周期连续播放，覆盖完整周期内部与相邻周期接缝。除计划明确允许的跳变外，接缝应保持姿态、位置、运动方向与速度连续，不重复保持端点，不由播放器加入计划外等待。仅确认首末帧位置相同不能证明循环通过。

缓动极值处短暂减速、有意停顿和终态保持按动作计划保留；未计划的定格、空白等待与重复端点应修正。不要自动删除所有相似帧，避免破坏低幅度运动或设计中的保持阶段。人工审阅分别判断阶段内运动、阶段连接、事件时刻与播放边界，不以某一类动作的运动模式要求所有动画。

## 视频节奏整理

当前 `video-to-atlas.mjs` 对输入视频整段抽帧，并使用同一 FPS 播放全部帧；没有时间区间选择、分段剪辑或独立播放速度参数。降低 `--fps` 同时减少帧数与播放速度，不能缩短动作。不要向工具传入不存在的裁剪或重定时选项，也不要只改报告中的帧率。

1. 保留用户原视频，核对已确认动作计划，记录各阶段、事件和停顿的实际源时间。源时长满足游戏时序时可直接抽帧，不额外变速。
2. 视频含前后等待、重复动作周期或段间未计划停顿时，用本地视频剪辑或 `ffmpeg` 先选择有效区间；多区间依原顺序连接，保持姿态接缝。源视频较长但内容完整时，按阶段重定时到计划区间，不能用整体加速掩盖不同阶段的节奏错误。
3. 将整理结果保存为独立派生视频，保留原视频路径与 SHA、派生视频路径与 SHA、实际剪辑命令或配置，以及每段源起止时间到游戏起止时间的映射。生成器的最短交付时长只影响源视频与映射，不改变已确认的游戏时长；不要用静止填充凑足时长。
4. 将派生视频作为 `--input-video` 与合同中的 `source_video`，报告 SHA 对应实际抽帧输入；原视频和时间映射保存在 Work Item 设计证据中。缺失动作或不能平滑连接时，记录缺陷并在正式帧阶段补齐/修正，不伪造已有源视频事件，也不默认重新生成视频。
5. 抽帧后核对 `帧数 / FPS` 与整组游戏时长（最多一个目标帧间隔的量化差）、各事件帧、阶段顺序和计划保持。偏差先修正时间映射或按来源顺序删去未计划保持帧，再交付人工检查完整行为、阶段连接与对应的单次/循环/终态播放方式；文件 SHA、格式校验和报告 `PASS` 不能证明节奏通过。

抽帧后才发现时间问题时，可以按来源顺序删去未计划保持帧，或在已有帧槽位修正过渡姿态；保留已修正图片，重新连续编号，并保留剩余帧真实的来源时间戳与 SHA，更新来源映射、图集、报告与预览。现有合同要求来源时间戳严格递增，不支持交换来源顺序、复制来源帧或无来源的新帧；需要这些操作时，先将编辑结果保存为新的真实视频来源，再抽帧、记录其 SHA 与来源时间，并迁移修图成果，不以改写来源字段绕过校验。为落实已确认时间轴而整理源视频不需要重新确认；改变游戏总时长、阶段节奏、关键事件或有意停顿则先更新灰盒并重新确认。
