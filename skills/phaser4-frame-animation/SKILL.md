# Phaser 4 视频抽帧动画

此路线先交付**可播放的动画灰盒预览**，等待用户确认当前动作方案，再进入视频提示词与正式资源制作。正式动画以**视频文件**为初始抽帧源；视频只提供动作流程草图与预期，不是最终动作验收标准。交付提示词后等待用户提供实际视频文件；收到文件后运行抽帧工具，交付网页预览供人工检查，再把图集接入 Phaser。灰盒只是动作设计工件，不得作为真实视频、抽帧来源或正式图集。

在当前 Work Item 范围内提出动画资源方案、审阅视频与抽帧预览、修复并重验；交付后回到控制面提交证据。

## 执行代理

帧动画 Work Item 的动作规划、灰盒制作、视频提示词、节奏整理、抽帧和修正交付，统一委派给 `gpt-6.1-sol`、`max` 推理强度的执行子代理。主代理负责整理需求与任务包、传递人工反馈和确认依据、协调接入范围、审查交付与最终验证，不自行接管动画制作。

使用 `collaboration.spawn_agent` 创建执行子代理，显式设置 `agent_type="default"`、`model="gpt-6.1-sol"`、`reasoning_effort="max"`、`fork_turns="none"`，并在 `message` 中提供完整任务包；不要使用模型固定为其他配置的专用角色代替。工具或指定模型不可用时报告限制，不静默换模型或降级推理强度。

任务包须包含当前 Work Item、目标与行为边界、素材和视觉基线的实际路径、本 skill 与必要参考文件路径、可修改文件范围、已确认的时间轴/候选 SHA、当前允许推进的步骤、验收标准、测试等级与命令、禁止操作及并行改动提醒。首次只推进到灰盒交付；用户确认后通过 `followup_task` 复用同一执行代理，传递确认记录并推进到视频提示词交付；收到视频后继续交接实际文件和后续制作任务。未确认或未收到视频时不能越过对应停止条件。

同一工作项的反馈修正、复验和连续制作优先复用该代理；工作项完成或范围发生实质变化时结束当前生命周期，新的工作项重新委派。位图生成/编辑仍按项目规定交给图片生成代理，帧动画执行代理负责提供时间轴、帧槽位和素材约束并集成结果；委派不扩大路径、视觉自动验证或外部操作授权。

## 生产顺序

1. 从当前游戏 Work Item 收集玩法场景、资源用途（角色/敌人/物件/特效）、现有美术风格与参考素材、游戏视角、主体在游戏中的显示尺寸、动作与事件时机、循环方式、目标 FPS、输出宽高和背景处理要求。先按[完整动作与时间轴](references/action-timing.md)确定动画组、整组游戏时长、内部阶段、关键事件、播放方式与允许保持，再做灰盒；同一完整行为的连续阶段共享时间轴，不按阶段或事件数量拆视频；独立行为按触发条件与生命周期区分。缺省值明确写为建议值；不要把未确认的参数描述为用户要求。
2. 先按[动画灰盒预览](#动画灰盒预览)生成低保真、可播放的动作样片，交付预览文件、动作参数和人工检查要点。**停在这里等待用户确认当前灰盒候选**；收到调整意见只修改灰盒并重新交付，不提前写正式视频提示词、生成正式美术、抽帧或接入 Phaser。
3. 用户确认后，依据确认的动作时序、锚点和运动范围写出一份可直接交给视频生成器的**游戏资源提示词**，而非宣传片或场景演示提示词。描述主体身份与游戏美术风格、镜头/视角、完整动作时序、玩家需要看清的阶段状态、事件反馈与结束方式、稳定的世界锚点、比例与画布位置、时长和画幅。提示词中要求呈现的主体、身体部位、道具、特效及其完整运动范围默认都不得被画面边界裁剪；只有用户明确允许裁剪某项内容时，才写明该项和允许的裁剪范围。独立精灵动画不要烘入游戏场景、UI、文字、镜头运动或环境阴影；如果任务本身是场景动画，则按场景图层合同描述背景与运动范围。
4. 保存提示词文本作为当前动画候选的工件，并将提示词交给用户。**停在这里等待视频文件**；不假定视频生成器或用户已生成视频。
5. 收到视频后核对文件能被解码，先按[视频节奏整理](references/action-timing.md#视频节奏整理)将有效动作区间映射到已确认的游戏时间轴，去除未计划的空白等待、重复周期和段间停顿，再设置抽帧 FPS、输出尺寸和 `--remove-background` 生成初始帧与图集。把动作流程、关键姿态、事件时机、入镜范围和缺陷记录为图片修正依据。姿态、造型或裁剪问题均可在抽帧图片阶段修复，不因此退回视频生成；时间问题不能只靠修外观或降低 FPS 处理。
6. 交付工具生成的 HTML，列出实时播放、逐帧缩略图和首尾衔接的人工检查要点；不自动截图或宣称视觉验收通过。根据人工反馈直接修正对应帧图片（或图集中对应 cell），包括姿态、动作轨迹、阶段时序/关键事件/终态、循环衔接、造型、背景与透明边缘；同时检查相邻帧连续性。保留可用帧，修正后更新图集、报告与预览再交付人工审阅。最终帧动画按游戏动作要求验收，不要求复刻原视频中的错误。抽样参数错误可从同一视频重抽，但不得覆盖已完成的图片修正。
7. 将 PNG 图集、JSON 报告、提示词、实际抽帧输入视频和网页预览绑定到当前 Work Item 的 `asset.frame_animation`，同时保留用户原视频、时间映射、灰盒及其确认记录，再按全局视觉工作流进入 Phaser 接入与验证。

全局阶段以[唯一控制面](../phaser4-game-workflow-control/SKILL.md)的 V0→V5 为准：V2 先完成动画灰盒人工确认，再确定提示词与资源计划；V3 等待并接收视频、抽帧与审阅；V5 接入 Phaser。灰盒确认、提示词审阅和视频交付不授予真机、发布、付费或其他外部操作权限。完整文件门见 [工作流接入合同](references/workflow-integration.md)。

## 动画灰盒预览

灰盒必须能播放实际动作，不能只交付文字方案、静态关键帧或视频提示词。优先复用项目已有的隔离预览能力；没有可用能力时生成无需启动服务即可打开的独立 HTML，用 Canvas/SVG 的简单几何形、轮廓或关节示意表现主体、道具和关键特效，不依赖正式美术或真实视频。灰盒不注册正式 Scene 入口，不承载正式业务逻辑。

使用计划中的视角、朝向、显示尺寸、共享画布、FPS 与固定语义根锚点，表达起手、玩法生效、收势、循环衔接或非循环终态。预览提供播放/暂停、重播与逐帧查看，标注关键事件时间或帧索引，并显示锚点和画布安全边界，便于人工判断动作节奏、运动方向和完整入镜范围。检查标记仅属于预览界面，不混入正式动画。

灰盒按整组游戏时长播放；完整展示行为的初态、连续阶段、关键事件、衔接与终态，不用独立阶段预览代替组合结果。按计划区分运动与有意保持；循环动画提供跨周期连续播放，检查周期内部、接缝速度和重复端点；单次动画检查结束与终态，有意保持须说明用途与时长。人工确认同时覆盖动作分组、总时长、阶段时间和停顿，不只确认造型。

保存预览与动作参数，绑定当前 Work Item 和候选版本，记录文件路径与 SHA、时长、FPS、尺寸、锚点、关键事件及循环方式。交付可打开的预览链接，并明确待确认项；没有用户明确确认时保留待确认状态，不以文件生成成功、超时、视频交付或其他候选的确认代替当前确认。收到确认后记录用户确认依据及对应候选文件 SHA；改变动作时序、关键姿态、事件时机、循环方式、锚点或运动范围须更新灰盒并重新确认，单纯细化正式美术不重复确认动作方案。视觉显示由用户人工验收，只有用户明确要求自动验证时才能自动截图。

提示词应先读取项目已有的视觉基线、角色设定、玩法事件和资源预算。动作要服务于游戏状态识别：运动阶段持续推进，有意保持须有明确时间与用途；多阶段行为须让阶段顺序、关键事件与过渡可辨；循环保持接缝连续，单次播放明确终态。主体的脚底接触点、安装点或其他语义根锚点应留在共享画布的固定位置，只有动作本身要求位移时才改变。所有被要求呈现的内容在每个相关画面中都应完整保留并处于安全边距内，包括动作扫掠到的武器和特效；若画幅容纳不下，应调整构图或画布规划，不能默认裁掉边缘。用户明确允许的裁剪必须逐项记录，不能扩展到其他内容。需去背景时要求与主体颜色明显不同的均匀纯色，避免色溢、接触阴影和颜色相近的半透明特效；不去背景时按游戏场景资源要求处理。生成视频的细节和运动平滑度须足够供目标 FPS 抽样，避免抽帧后动作信息丢失。

可按以下结构输出，方括号内容必须用当前任务的具体要求替换，不得保留占位符作为成品。只有用户明确允许裁剪时，才把模板中的“不得裁剪”改为逐项列出的例外及范围：

```text
为[游戏项目/玩法场景]制作可抽帧的[角色/物件/特效]动画资源，沿用[参考素材和美术风格]。
本次制作一个完整的[动作组名称]，内部含[连续阶段及次数]；阶段之间按确认的连接条件衔接，不因阶段数量拆成独立视频，不插入未计划的初态重置、重复准备或等待。
整组游戏动作总时长为[毫秒]，目标播放与抽帧 FPS 为[数值]；视频交付时长为[秒及依据]、画幅为[宽高比]；主体在游戏中约显示为[尺寸]。若受视频生成器时长限制，按[源时间到游戏时间映射]处理，不据此拉长游戏动作。
保持[游戏视角、朝向、比例、关键造型]，使用固定镜头、固定画布和[脚底/安装点/语义根]锚点。
动作按整组时间轴依次为[各阶段开始/结束时间、姿态与衔接]，关键事件为[事件名称、作用与时间，无则写无]；仅在[已确认的时间区间与用途，无则写无]保持姿态。
[循环动画：按已确认周期播放，姿态、位置与运动趋势按接缝合同衔接，不增加计划外等待或重复端点；非循环动画：按计划结束并到达或保持已确认终态。]
让玩家在目标显示尺寸下看清[轮廓、攻击方向、交互反馈等关键状态]；上述所有要求呈现的内容及其完整运动范围始终位于画面内并保留安全边距，不得裁剪。
背景为[用于去背景的高对比均匀纯色，或任务要求的独立场景背景]。
不要加入 UI、文字、额外角色或无关场景元素；避免跳切、镜头移动、闪烁、形变、缩放、无意漂移和出框。
```

## 抽帧工具

工具需要本机可调用 `ffmpeg` 和 `ffprobe`，并使用项目已有的 `sharp` 依赖处理图像。先运行帮助查看当前参数：

```powershell
node <skill-dir>/scripts/video-to-atlas.mjs --help
```

示例：

```powershell
node <skill-dir>/scripts/video-to-atlas.mjs `
  --input-video art/hero/attack.mp4 `
  --output-sheet public/assets/hero-attack.png `
  --output-report evidence/hero-attack.video-atlas.json `
  --output-preview evidence/hero-attack.preview.html `
  --fps 12 `
  --width 128 `
  --height 128 `
  --remove-background `
  --background-color '#00ff00' `
  --animation-key hero-attack `
  --texture-key hero-attack `
  --runtime-url assets/hero-attack.png
```

`--fps` 同时控制每秒抽取帧数与报告中的播放帧率，和源视频帧率无关；降低它不会缩短游戏动作。输入必须先按已确认的游戏时间轴整理，不能将生成器的长视频原样当作游戏周期。`--width` 与 `--height` 同时填写时按指定像素尺寸输出；只填一个时等比缩放。不开启 `--remove-background` 时保留视频画面背景。开启时，背景色和容差应按实际视频检查；纯色背景更适合此处理，复杂背景可对抽帧图片进行专门抠像或图片修复；不因背景处理失败重新制作视频。

图集使用固定大小的水平 cell；尺寸过大时工具应明确拒绝并要求降低帧数或尺寸。报告记录源视频和图集的 SHA、抽帧参数、每帧身份及 Phaser `preload`/`anims` 合同。网页预览用于浏览器人工检查，不等于真机验收。

`--runtime-url` 填游戏实际部署时读取图集的 URL，并在资源清单的 `spritesheet.runtime_url` 中使用相同值。输出 PNG 的本地路径不一定等于网页 URL。

## 抽帧后的图片修正

若修正改变已确认的动作方案，先更新灰盒并重新取得用户确认，再修改正式帧；沿用已确认动作方案的局部纠错和外观细化直接按下述流程处理。

视频仅表达期望的动作流程，抽帧图片是后续正式制作与修正对象。动作有问题也修改图片，不默认重新生成视频；只有用户要求更换动作草图来源时才替换视频。可以修正姿态、运动方向、关键动作与首尾衔接，不把视频缺陷当作必须保留的事实。按修正目标检查对应帧及其相邻帧，保持最终动画连续，并维持当前 FPS、cell 尺寸与锚点合同；未计划停顿可按来源顺序移除保持帧，过渡姿态可在已有帧槽位修正，保留已有修图成果。需要新增帧或改变来源顺序时，按视频节奏整理生成新的抽帧来源并迁移修图，不伪造来源时间戳。帧数、索引或时间映射变化时，更新实际产物、来源记录与合同，不沿用旧数据。不要重新抽帧覆盖已完成的图片修正。完成后更新图集及其 SHA、报告和预览绑定，再按游戏动作要求验收。具体证据更新见[工作流接入合同](references/workflow-integration.md)。

## Phaser 接入

按报告中的 `phaser.preload` 调用 `this.load.spritesheet`，按 `phaser.anims` 调用 `this.anims.create`，并使用报告的 origin 设置 Sprite。图集帧序从 0 连续编号；循环动画检查最后一帧回到首帧的观感。运行态事件、播放状态与性能仍在全局 V5 验证。
