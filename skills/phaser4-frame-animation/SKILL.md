# Phaser 4 通用帧动画制作

使用统一生产流程，按用途选择制作、优化和人工验收规则，来源默认使用视频抽帧。视频作为动作草图；用户明确选择图片路线时，以真实生成的首尾、阶段关键帧及双图参考补帧形成序列。最终动画以游戏要求和视觉基线为准。当前 Work Item 的资源交付回到既有控制面，不另建动画状态机。

在当前 Work Item 范围内提出并确认动作时间轴设计，审阅真实视频或关键帧及完整序列，修复并重验；交付后回到控制面提交证据与状态迁移。

## 分类入口

每个动画先确定用途类型，只读取对应分类参考；多类型批次逐区域选择规则，不默认加载四份文档。

| 用途类型 | 选择依据 | 读取参考 |
| --- | --- | --- |
| 普通动画 | 物件、环境、装饰、机械运动与状态变化 | [普通动画](references/object-animation.md) |
| 角色动作动画 | 待机、移动、攻击、受击、跳跃等身体行为 | [角色动作动画](references/character-animation.md) |
| 特效动画 | 命中、爆炸、烟尘、光效、状态效果等视觉反馈 | [特效动画](references/effect-animation.md) |
| UI 帧动画 | 按钮反馈、提示、图标等需要逐帧位图资源的界面动效 | [UI 帧动画](references/ui-frame-animation.md) |

用途类型不决定来源路线、行为单元、生成批次数量或运行时动画 key 数量。循环、单次、组合、终态保持是各类型共用的播放参数，可按任务组合使用。角色动作可进一步按循环运动、主动行为、被动反应和连续组合选择规则，不为每个动作新增技能。简单程序 UI 动效按既有 UI/程序路线处理。

## 来源路线

用户未指定来源时默认使用视频抽帧，并在动作时间轴设计中记录；图片递归补帧仅在用户明确选择或确认切换时启用。已有当前任务明确确认的来源沿用记录，切换按既有方案变更与时间轴设计确认处理，不因默认值变化丢弃已确认成果。视频来源或生成能力暂缺时报告缺口，不能自动改用图片路线。两条路线共用分类、游戏时间轴和人工验收，只读取当前来源细节。

| 来源 | 适用依据 | 按需读取 |
| --- | --- | --- |
| 视频抽帧（默认） | 使用真实视频作为连续运动草图；选择有效区间并按阶段重定时后抽帧 | [视频节奏整理](references/action-timing.md#视频节奏整理)、[按区域抽帧](references/region-planning.md#按区域抽帧) |
| 图片递归补帧（明确选用） | 用户选择逐个控制关键姿态、造型或透明边缘；固定画布依次制作首尾、必要关键帧，再用相邻两图生成指定帧位 | [图片递归补帧](references/image-inbetween.md) |

图片路线的“插帧”是带双图参考和指定动作时点的图片生成，不是保证几何正确的光流插值。跨视角、接触、遮挡或相同首尾的循环先补必要关键姿态，再递归；不只凭首尾推断完整复杂运动。

## 共用流程

1. 读取视觉基线、用途类型参考与[完整动作与时间轴](references/action-timing.md)，建立当前动画的设计工件。明确来源路线、行为边界、初态/终态、游戏时长、阶段区间、关键姿态、事件、播放方式、锚点/允许位移、完整运动范围、目标显示尺寸、FPS 和背景处理。角色动作还须明确前后动作衔接、是否循环及进入/退出条件，见[衔接与循环设计](references/character-animation.md#衔接与循环设计)。按需要读取[区域规划](references/region-planning.md)，合批时各区域仍有独立类型和时间映射。
2. 先按[动作分析规则](references/action-timing.md#先分析动作再确认)解释行为边界、阶段与运动依据、衔接/循环及节奏取舍，再交付建议时间轴、事件时点、关键姿态意图和尺寸推理。视频同时交付 768p/2K 的区域排布、条数、整组消耗比较及推荐方案。**等待用户确认当前动作分析与时间轴设计工件**；调整意见只推进分析与设计修订，不制作帧动画灰盒或可播放几何示意。
3. 当前动作分析与时间轴设计确认后，按“共用视觉与资源约束＋类型规则＋当前动画参数”编写正式提示词。视频按[分辨率与合批比较](references/region-planning.md#视频条数与消耗比较)推理选择 768p 或 2K：先最少条数覆盖全部动作，再在该条数下选整组消耗最少者，同等条件优先 768p；推荐方案随设计一并确认，不另设 2K 询问门。图片仍按[图片分辨率约定](references/region-planning.md#图片分辨率约定)处理。画幅、声音与时长按任务记录。视频提示词交付后等待实际视频；图片制作在已有生成授权范围内委派图片代理，缺少授权时停在可审查提示词与计划。
4. 视频路线接收真实视频并核对画布、区域与音轨，按需要选择有效区间、阶段重定时并保存派生来源，交付用户人工验收实际最终抽帧输入。原视频已适配时直接验收原视频；只有实际视频内容、区域和时间映射已经人工验收才抽帧，SHA 不参与验收。未通过先修正并重提，确认修正方案不能放行抽帧。图片路线核实实际输出尺寸，固定统一画布并确认首尾；同一连续行为的必要关键帧按时间顺序逐张制作，与真实基线及相邻已确认帧比较，人工确认当前帧后才推进下一关键帧。关键帧齐备并确认后，再按已确认时点递归补齐目标帧位。实际依赖与[一致性及衔接门](references/image-inbetween.md#关键帧的一致性与衔接门)集中维护；父图有缺陷先修正，不继续传播。
5. 视频按固定区域抽帧，图片按真实来源清单打包；两者共用背景处理、等比缩放、固定 cell/锚点、独立图集、报告和 HTML 预览。依据当前类型反馈局部修帧，保留已有修图成果及来源身份，更新图集、报告、预览和 SHA。缺陷修复不默认替换整组来源。
6. 用真实完整帧序列人工检查节奏、连续性、事件及单次/循环/终态和外部动作衔接。保存分类规则、时间轴设计确认、真实候选审阅、时间映射与最终人工验收证据，按[工作流接入合同](references/workflow-integration.md)提交资源，再回到控制面完成 Phaser 接入和运行验证。

## 设计确认与真实素材验收

时间轴设计确认只批准当前动作参数与制作方案，不证明姿态、重量感、比例稳定或连续性。视频路线以真实视频候选审阅动作，图片路线以真实首尾和关键帧逐张确认；两条路线最终都用完整真实序列验收。真实序列预览提供播放/暂停、重播和逐帧查看，检查标记只放预览界面。正式美术使用真实基线及已确认素材，设计图表和历史占位示意不得作为生图视觉参考。详细要求见[动作时间轴设计确认](references/workflow-integration.md#动作时间轴设计确认)、[真实素材审阅与验收](references/workflow-integration.md#真实素材审阅与验收)及[设计与美术的边界](references/workflow-integration.md#设计与美术的边界)。

## 共用质量与关键约束

- 以可读性、节奏、主次关系、连续性和事件同步验收；具体判断及优化方法见[共用质量与优化](references/action-timing.md#共用质量与优化)。重量感、夸张程度、停顿和跟随运动按类型、对象性质与视觉基线配置，不统一套用战斗节奏。
- 游戏时间独立于源视频时长。完整行为共享时间轴，内部可标事件和输入衔接；制作分组不增加攻击次数、自动连击或伤害，也不改变现有输入机制。
- 时长、阶段比例、命中停顿、连击次数与音频均由当前任务确定；具体动作和参数案例不能成为全局默认要求。视频在 768p/2K 中按实际区域排布、条数与整组消耗选择，不以固定档位、压缩运动范围或丢失必要细节凑批次。图片分辨率约定保持独立。图片序列没有视频音轨，声音独立绑定事件。
- 默认保持要求呈现的内容及完整运动范围入框，保留安全边距。裁剪例外须有当前任务的明确授权，逐项记录对象、范围与理由；不能为合批或强调力度自行裁边。
- 稳定锚点不等于禁止运动。允许位移、姿态夸张或形变须在设计工件中说明范围和意图，按计划验收；禁止未计划的漂移、闪烁、比例变化与跨区串入。
- 固定画布、相同锚点记录和来源校验通过，不证明实际对象尺度、支撑位置或动作连续。图片路线先确认当前帧的类型相关状态与相邻衔接，再放行依赖它的制作；不能以增加补帧、逐帧缩放居中或静止复制替代纠错。
- 背景处理按素材边缘与类型选择。颜色去背景只用于已确认的纯色硬边；半透明、发光或未知边缘使用真实 Alpha、遮罩或帧图片修正，不冒充硬边确认。特效、声音和镜头反馈是否烘入按任务合同决定。
- 分类与优化参数保存在设计工件，不因分类添加合同字段，不虚构脚本或生成 API 参数。视频沿用原合同；图片使用独立来源清单、报告和 accepted 合同，记录真实生成图、父图、时间槽位、生成/修图记录与 SHA，不能伪造视频路径或来源时间戳。
- 时间轴设计与真实素材显示由人工确认或验收；文件门只验证结构与身份。不得自动截图或启动真机验收，外部写入、付费、发布沿用独立授权边界。

## 执行代理

帧动画 Work Item 的时间轴设计、提示词、时间整理、抽帧/图片序列集成和修正仍统一委派给 `gpt-6.1-sol`、`max` 的执行子代理。主代理负责需求、任务包、人工反馈、接入范围、审查与最终验证，不接管动画制作。

使用 `collaboration.spawn_agent`，设置 `agent_type="default"`、`model="gpt-6.1-sol"`、`reasoning_effort="max"`、`fork_turns="none"`。完整任务包包含 Work Item、用途类型与来源路线、对应参考、行为/输入边界、素材与基线路径、允许修改范围、当前候选版本/时间轴、确认依据、允许推进步骤、验收标准、测试等级与命令、禁止操作及并行提醒。首次只交付动作时间轴设计；确认后通过 `followup_task` 复用代理写提示词；视频路线交接当前真实视频及人工审阅结果，图片路线交接当前已确认帧及实际生成授权继续制作。

同一工作项的连续修正优先复用代理；范围实质变化或工作项完成后结束该生命周期。位图生成/编辑仍交给图片生成代理，动画执行代理提供时间轴、帧槽位和素材约束并集成结果。指定工具或模型不可用时报告限制，不静默换模型。委派不扩大文件、视觉自动验证或外部操作授权。

## 本地工具与参考路由

视频抽帧需要 `ffmpeg`、`ffprobe` 与项目 `sharp`；图片规划只使用 Node.js，图片打包使用 `sharp`。先查看当前路线的实际工具帮助：

```powershell
node <skill-dir>/scripts/video-to-atlas.mjs --help
node <skill-dir>/scripts/image-inbetween-plan.mjs --help
node <skill-dir>/scripts/images-to-atlas.mjs --help
```

视频工具每次处理一个区域（省略则为整画布），覆盖完整输入时间段；`--fps` 同时控制抽样与播放，没有时间剪辑或独立逐帧时长参数。图片规划先确定游戏时长、FPS、关键帧位和递归依赖；图片打包从来源清单取 FPS/loop，只处理实际图片，不生成素材。时间问题先按共用时间轴修正设计与来源，不只改报告。
